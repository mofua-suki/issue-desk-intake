# 実装中の質問への内部回答

受付は実装の回答待ちを既存の自動復旧周期で確認する。依頼本文・受入条件・コメントに根拠がある事実や規約の質問には、実装担当へ直接回答する。質問と根拠の対応を確認し、受入条件を減らしたり新しい承認を与えたりしない。

自動復旧AIの `reply` は、`evidence` に種類と原文引用を持つJSON文字列を返す。種類は `fact`・`convention`・`pastDecision`。`sources` は `source: "body"` または `source: "comment"` と `quote` を持つ。コメントには `detail.comments` の0始まりの `index` を指定する。コントローラーは引用が現在の入力に実在することを確認する。引用だけで回答の妥当性を証明するものではなく、AIは質問との関連と受入条件の維持も確認する。

`pastDecision` は新しい承認ではなく、起票前に記録された判断の説明である。`approvalId` で完了計画の `before_implementation` の事項を参照する。次のすべてを確認する。

- コントローラーが保存した `completionApproval` の送信元が `screen-session` で、記録に発言ID・原文・日時がある。
- 了承した計画のfingerprintが現在の計画と一致する。
- 起票時の最終本文SHA-256が現在のIssue本文と一致する。
- `conditions` の1件の原文引用が、保存された条件と一致し、現在の本文またはコメントに存在する。

PCトークンやCLIキーからの了承記録は実利用者本人と断定しないため、過去判断としての自動回答には使わない。複数の過去発言を引き継いだ計画では、代表送信元ではなく、参照する事項の発言ID・原文・日時と送信元を個別に照合する。外部環境など、保存記録だけでは現在の成立を確認できない前提も本人へ戻す。差分・対象SHA確定後の承認は事前計画で代替しない。削除・権限・上限超過などの既存の個別認可経路も維持する。

判断開始時に本文・コメント・実装結果・完了計画・了承記録・起票時の証拠を固定化し、送信直前に再取得して比較する。変化があれば古い回答を送らず、変更理由を記録する。同じ原因の回答は自動復旧台帳で1回に制限し、結果が不明な送信も再送しない。有事の期限切れ処理の自由文の根拠には、この質問専用JSON形式を適用しない。

## 検証

`server/internal/operations/job_recovery_question_test.go` は、根拠付きの質問回答を本人の仲介なしに1回送れること、捏造した引用・新規承認・不明な記録の拒否、計画・起票本文・了承記録・条件の変化を検証する。過去判断の成功ケースは `completionplan.Plan` とコントローラーの `Confirmed` が実際に生成した了承記録を使う。
