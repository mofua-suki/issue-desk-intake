# プロジェクト一覧の表示スナップショット

`GET /api/projects` は、一覧レコードのDB読取と各行のrunning・作成可否・番号解決関数の取得までをService共通mutex内で行う。DBから復元したレコードは要求専用であり、全行の状態取得後にmutexを解放する。全文clone、actionsと表示フラグの組立て、各IssueのDeskNumber照会はその後に行う。整形処理はServiceを参照しない。

作成可否はOptionsの設定から求めたboolを保持する。OptionsはNewに渡して以後固定する。番号台帳の照会結果自体を一覧のDBスナップショットに含めるものではなく、番号未解決時はdeskにnullを設定する（DeskNumber未設定なら保存レコードの値を保持する）。順序、全文、空配列、HTTPヘッダーとステータスは一覧の整形の前後で同じにする。

単一GETとcreate/mutate（冪等応答を含む）のpresent呼出しは引き続き共通mutex内で行う。非同期処理の開始・完了と永続化も既存の排他に従う。一覧の整形が番号解決を待っている間も、番号解決を必要としない別プロジェクトの操作は進められる。

## 配備環境での計測

運用担当者が同じネットワーク経路から、変更前と配備後の両方で実行する。対象は実際に利用するServerと番号台帳であり、片方だけの結果から改善率は算出できない。画面セッションのCookieを `ISSUE_DESK_MEASURE_COOKIE` に設定し、番号照会が不要な別プロジェクトのIDを指定する。Cookieは秘密情報として扱い、共有ログや結果ファイルに記録しない。サンプル数は両期間で揃え、運用への負荷を考慮して決める。

```sh
node scripts/measure-project-list.ts http://intake.example PROJECT_ID 100 > measurements.json
```

各サンプルで一覧GETと単一プロジェクトGETを同時に開始し、本文の受信完了までの時間をミリ秒で記録する。200以外は失敗として終了する。結果には各時間とp50・p95が含まれ、Cookieと応答本文は含まれない。前後それぞれの結果を別の安全な場所に保存し、配備版、時刻、サンプル数、一覧の件数、番号台帳の状態、同時負荷と通信経路を記録する。条件が異なる場合はその差も報告する。

一覧と単一GETのそれぞれについて、同じ分位点の改善率を `(変更前 - 変更後) / 変更前 * 100` で算出する。単一GETの時間は同時操作の応答時間であり、mutexの待ち時間そのものではない。要求開始は同時でもServerでの処理が重なる保証はないため、分布と負荷を併せて解釈する。画面の初期表示時間には通信・描画なども含まれるので、このHTTP計測だけで画面全体への寄与や因果関係は確定できない。画面の実測も同じ条件で前後比較する。
