# Go Serverの照合周期

## 前提成果物の保留の観測

Serverは起動時と1分ごとに前提成果物の保留を観測する。直近6時間に識別値や世代のない保留履歴がある場合、その仕事の観測は失敗し、既存の検知記録を保持する。他の仕事の観測は続け、周期処理全体を失敗として記録する。次の周期で再確認し、不完全な履歴が期間外になっても、現在の保留イベントが識別できない場合は観測失敗を維持する。観測は仕事の再実行を行わない。

## リポジトリの注意点

起動時と既存の起票結果照合の1分周期で `reviewnotes.Service.Run` を呼ぶ。
照合後に日次処理を別のgoroutineで開始し、実行中は重ねて開始しない。タイマーは
増やさず、日次処理がAI枠を待つ間やAI実行中も、起票結果照合は次の周期に進む。
日本時間で各リポジトリ1日1回だけ試み、既知の分類を元の行まで照合して再利用し、
未知だけを道具なしのAIで分類する。既存のAI枠・注意点の更新の固定モデル（工程 `reviewNotes`、haiku相当・low）・一時切り替えを使い、
使用量を「注意点の更新」として記録する。日次処理も周期処理の待機対象に登録する。
周期停止では新たな日次処理を開始せず、起動済みの処理をキャンセルして終了を待つ。
業務用の寿命は維持し、受理済みの起票や復旧処理は結果を保存できる。通常停止では
業務サービスと周期処理を終了してから保存先を閉じる。
分類失敗時は試行日以外を保存せず翌日に再処理する。採用・期限・保存と復旧の詳細は
`server/internal/reviewnotes/README.md` を参照する。新しいタイマーは追加しない。

## 移管成果物の開始条件

Serverは30秒ごとに受付の案記録と移管の開始条件を照合する。資料を読めない依頼は未知のまま止め、無関係とは判断しない。判断が必要な項目は通常のhold相談に渡す。

相談IDはジョブIDと照合キーから作る安定したUUIDで、最初のメッセージにも同じIDを使う。アプリ用スキーマの相談保存、メッセージ保存、共有DBへの相談ID反映の間で停止しても、再起動後に同じ相談とメッセージを再利用する。thinkingで保存された相談はEngineで再開する。相談だけで起票・依存解除を実行しない。

採用する回答は `intake_waiting`・`draft`・`submitted` の最後のassistant発言だけ。holdの案内末尾とJSONコードフェンスを取り除いてから、relationが `required` または `unrelated`、evidenceが空白でなく4000 UTF-16文字以内であることを確かめる。不明な回答や検証に落ちた回答は開始条件を解除しない。共有DBへの反映時にもジョブがqueuedで、同じ照合キーが残っていることを確かめる。

## 外部アプリの既定ブランチ

Serverは起動時と5分ごとに、担当表のdeployHostとそのホストのfleet設定にあるautoDeployが両方そろうアプリを確認する。Giteaのリポジトリ情報から既定ブランチを取得し、ブランチ名をURL符号化して最新コミットを読む。手動マージも同じ確認で拾う。

登録は自動マージと共通の `hostd.EnqueueDeployment` を使う。同じリポジトリ・コミットは重複登録せず、新しいコミットでは未着手の古い配備をsupersededにする。liveCheckの設定がなくてもautoDeploy対象のマージは登録する。

`issue-desk`・`issue-desk-worker`・`issue-desk-intake` は、ホストやコンテナの専用更新と二重にならないよう対象から除く。読取に失敗したアプリの配備は推測で作らず、他の対象は確認を続ける。

## 止まった依頼の自動復旧の記録

復旧の予約と結果は PostgreSQL の `settings` の `job-recovery` に保存する。
送信前の対象・台帳・DBの読取または AI 呼び出しの一時エラーは `pre_send_error` とし、同じ世代・原因でも次周期に判断し直す。連続3回の送信前エラー後は `skipped` とし、同じ世代・原因の自動再試行を止める。不正な判断や `none` は `skipped` のままとする。
送信結果が不明な場合は再送しない。`reserved` が1時間以上残った場合、次に同じ依頼の予約を試みた時に `send_unknown` に変える。元の原因は再送せず、異なる原因は判断できる。予約時刻が欠ける旧記録も不明扱いとする。各処理の締め切りは予約期限の半分とする。送信結果が不明な場合は送信結果の調査が必要。

## 別色で受け付けた相談の再開

起動側のwriter leaseが単独実行を開始した後、EngineのRecoverが初回走査と
10秒周期の走査を開始する。Engineの生成やBindEngineだけでは周期走査を開始しない。
Recoverには単独実行用のcontextを渡し、担当喪失で走査と新規取得を止める。
停止時は既存のQuiesceが新しい取得・AI開始を止め、取得準備・初回発言の保存・
開始済みAIの結果保存と通知まで待つ。待機のcontext終了でAIを一括取消ししない。

受領JSONの`claim`は`instanceId`と`acquiredAt`の取得印を持つ。旧JSONにも追加でき、
テーブル変更やデータ移行は不要。初回Chatとthinking再開が同じ取得印を使い、
結果保存と`handed`への更新を同じトランザクションで確定する。印が変わった旧結果は
保存・通知・後続の起票に渡さない。旧版の`handed`かつthinkingの下書きも照合対象となる。
取得印を交代するトランザクションで旧`run`も失効させるため、後続のAI開始前から
旧AIの途中回答・代理回答の保存を拒否する。

EngineはPostgreSQLの接続1本を生存確認用のトランザクションに使う。このロックは
受領の期限切れ再取得だけに使い、色の担当選出は従来のwriter leaseが担う。
処理中やQuiesceの保存待機中は、取得から90秒を超えても再取得しない。
Quiesceの完了・Engine終了・接続切断で生存確認ロックを解放する。
生存確認接続が切れた場合は失敗したトランザクションを破棄し、同じインスタンスの
ロックを取得し直してから次の受領を取得する。DB障害時も周期走査は残り、復旧後に
再試行する。先に後続Engineが取得印を交代した場合は、その印と旧runの失効を尊重する。

停止後の復旧では受領JSONや送信IDを消さず、共有DBを使う次の担当Engineを起動する。
取得時刻から90秒を厳密に超え、旧Engineの生存確認ロックが解放されると、次の走査で
条件付きで取得し直す。停止直後の再送や印の手動消去は不要。初回発言が保存済みなら
同じ発言を再利用する。取得印のない旧受領・受領のない古いthinking下書きも再開できる。
明示停止後に破棄、またはTODOへ戻した相談は、既存の撤回記録を下書き作成時に
照合して再作成を拒否する。残った受領は次の走査でrejectedとなり、AIを再実行しない。
受領・取得印・撤回記録の手動削除やデータ移行は不要である。
