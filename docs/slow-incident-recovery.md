# 遅延有事の起票結果の照合

遅延有事の要対応に「起票送信の成否を確認できません」と出た場合、予約の送信IDと対象プロジェクトを控える。送信担当が動いている可能性もあるため、予約や送信意図を削除せず、同じ内容を再投稿しない。`unknown` は失敗の確定ではなく、`reported` がない予約も要対応に残る。

運用担当者は対象プロジェクトのIssue履歴と受付の送信記録を確認する。有事の予約は共有DBの `settings` の `incident-deadline`、送信意図は受付のRecords DBの `slow_incident_filings` にある。受付自身が投稿したIssueの本文中の最後の起票マーカー `<!-- issue-desk:送信ID -->` と保存済み送信意図の両方が一致し、一意に見つかった場合にだけ照合で成功を記録できる。履歴の取得エラー、該当なし、重複、送信意図の欠落は起票されなかった証明にならない。接続や権限など照合失敗の原因を復旧し、再照合する。照合は投稿しない。

受付は周期処理で未確定の予約を照合する。照合は内部連携の `IncidentActions.RecoverSlowIncidentFiling` に有事IDと起票サービスを渡し、終了済みの元作業も対象にできる。運用者向けの照合コマンドやAPIはないため、照合できない場合は有事ID・送信ID・対象と確認結果を保全して開発担当へ引き継ぐ。記録を直接書き換えて成功や失敗にせず、結果を確定できない間は要対応を維持する。送信意図がない場合も自動再送はできないため、手動対応の要否は利用者に確認する。対象の正のIssue番号を確認できない遅延作業は自動起票しない。

成功が確認されると起票番号と結果が記録される。直接PRが必要な判定では成功後も要対応が残るので、その作業を別途確認する。
