# チャットとLinux PCへの配布

チャット用のSkill・常設指示・フック・受付CLIの正本はこのIntakeリポジトリに置く。実装を動かすWorker本体・compose・局所更新・hostdはWorkerリポジトリに置く。WorkerへServerの起動方法やDB接続を配らない。

## APIと操作の仕様

APIはこのリポジトリの`api/openapi/`に経路ごと、`api/openapi.json`に結合版を置く。チェックアウトが無い場合は tailnet 内の認証付き GET `/api/openapi.json` で結合版を取得でき、`?pathPrefix=%2Fapi%2Fissues` で経路を前方一致に絞れる（参照用 components は残る）。PC別トークン・一時キー・画面セッションを利用できる。認証方式と運用代行の条件を該当経路で確認し、操作には既存の`scripts/`を優先する。スクリプトが無い操作は`issue-desk-api` Skillに従い、同じAPIの認証・所有者・revision・送信IDの条件を守る。Workerの導入・実行・更新はWorkerリポジトリのREADMEと`deploy/`が正本で、Serverの配置手順は配らない。

新規相談に読取済み資料を添える方法は [read-evidence.md](read-evidence.md) を参照。

## GitHubからGiteaへの取り込み

既存のGit認証を用意し、Giteaに空の通常リポジトリを作る。参照元と宛先、取り込む枝が正しいことを確認し、宛先の対象枝が無ければ `empty`、存在すれば `git ls-remote --heads <宛先> refs/heads/<枝>` で確認した完全なSHAを指定する。URLに資格情報を埋め込まない。

```sh
node scripts/github-import-to-gitea.ts --source <GitHub参照元> --destination <Gitea宛先> --branch <枝> --expected-destination <SHAまたはempty>
```

対象枝のみ通常のpushで更新する。出力の対象枝と参照元・結果SHAを確認する。同一SHAの再実行は可能。宛先だけのコミットや分岐は拒否するため、差分を確認して解決する。失敗や中断後は送信済みの可能性があるので、両側の `git ls-remote --heads` で対象枝を照合してから、確認した宛先SHAで再実行する。並行して更新する運用者がいないことを確認する。完了後、Giteaで対象枝を既定枝に設定する。受付の候補外の既存リポジトリは管理者による受付許可リストへの追加が必要であり、具体的な登録手順は管理者に確認する。

## GiteaからGitHubへの公開

既存のGitとGitHub CLIの認証を準備し、資格情報をURLへ埋め込まない。統合枝の指定SHA、公開先の `owner/repo`、既定枝とその現在のSHAを確認する。コマンドは指定SHAまでの変更を公開先の基点に重ねた候補を計算し、対象・基点・統合元SHA・ツリー指紋・変更パス・確認値を表示する。プレビューは送信しない。

```sh
node scripts/github-publish-from-gitea.ts --source <Gitea参照元> --branch <統合枝> --source-sha <SHA> --repository <owner/repo> --base-branch <既定枝> --base-sha <SHA>
```

表示した内容を確認し、送信の個別承認を得た後、同じ引数に `--confirm <確認値>` を加えて実行する。確認値と再計算した候補が異なる場合、基点の移動、競合、差分なし、参照不一致は停止する。表示されたPR URLと確認対象SHAを確認し、GitHubの既存の必須チェックとレビューが完了してから通常の手順でマージする。このコマンドはマージしない。

中断や送信結果の消失時は同じ引数と確認値で再実行する。専用枝と既存PRの対象、基点、先頭と候補を照合し、一致しなければ上書きせず停止する。PR作成成功後に照合が失敗した場合はGitHubで状態を確認し、同じ引数と確認値で再照合する。既存PRが閉じられた場合やマージ済みの場合はその状態を表示して停止するため、GitHubで確認する。基点が変わった場合は新しい基点でプレビューし、内容を確認して個別承認を得直す。同じ候補の送信は複数の運用者が並行して実行しない。

## マージ後のGiteaへの再取り込み

GitHubで対象PRがマージされたことを確認し、公開時の統合元SHAと候補木、PR番号、GitHub既定枝の現在SHA、Gitea統合枝の現在SHAを控える。対象と受付登録は上記の取り込み手順に従う。GitHubのPR用枝が削除済みでもPR参照を読み取る。

```sh
node scripts/github-reconcile-to-gitea.ts --source <Gitea参照元> --branch <統合枝> --source-sha <公開時の統合元SHA> --destination-sha <Gitea現在SHA> --repository <owner/repo> --base-branch <GitHub既定枝> --base-sha <GitHub現在SHA> --pr <PR番号> --candidate-tree <公開候補木>
```

表示された対象と候補木を確認し、同じ引数の先頭に `--apply` を加えると指定Gitea枝へ通常pushする。実行後の結果SHAを次の公開プレビューの統合元SHAに使う。停止・中断時は送信済みの可能性があるため、両側の対象枝を `git ls-remote --heads` で確認する。競合や不一致の原因を解消し、現在の両SHAを指定してプレビューから再開する。再取り込み済みなら再実行しても枝を変更しない。

## Claude APIキーの受付登録

NASホストで本人が対話端末から `bash deploy/nas/set-claude-api-key.sh set` を実行し、表示されない入力欄にキーを入れる。再実行すると置換する。Ctrl-Dで入力を取り消せる。消去は `bash deploy/nas/set-claude-api-key.sh clear`。稼働中の書き手を一意に確認でき、受付の管理CLIを実行できる既存のDocker権限が必要。値は標準入力で管理CLIへ渡し、共有状態ボリュームの受付トークンと同じ保護領域へ保存する。blue・greenはこの領域を共有する。

失敗した場合は稼働書き手と受付の状態、保護領域の所有者・権限を確認する。失敗表示だけで保存状態を推測せず、状態を確認してから再操作する。配布APIは未登録・登録済み・消去済みを区別する。取得記録 `claude-api-key-reads.jsonl` は保護領域にあり、PC名・版・UTC日時だけを残す。取得記録はWorkerへの配置完了を意味しない。記録先の破損や書込不能から復旧するときは受付を停止し、記録を同じ保護領域内で退避して原因を解消する。受付の再開後、取得成功で記録ファイルが0600で再作成されることを確認し、退避記録も同じ保護を維持する。Worker側の取得・反映への対応が完了するまでは、各PCの既存の配置手順が必要。

利用前に本人が対象組織とworkspace、支出制限、当月の付属クレジット、購入済み残高、auto-reloadを確認する。契約上限内かつ確認できた当月の付属クレジット内だけで使用し、追加購入・追加入金はしない。追加出費を防げる条件を確認できなければ開始しない。

## 要対応と受付側の監視

`node scripts/desk-alerts.ts --json` はIssue・相談・クローズ依頼・利用量の見直し・全部のテスト・止まり・自動処理を画面と同じ規則で分類する。`items` は利用者の判断または原因別の引継ぎ、`monitoring` は受付側が扱う記録で、未知の種類もこちらに保持する。件数と絞り込みは表示対象に適用する。自動で続かない停止中の相談は引継ぎに含め、実行中・再試行予定・子を持つ親相談は監視に残す。その他は失敗や下書きという状態だけでは要対応にせず、相談の質問、クローズの確認、上限追加、明示された本人判断、未了承認を表示する。引継ぎをまとめた行の `attentionMembers` は元の対象・理由を保持する。

未了承認はID・対象head SHA・理由を表示し、画面のAは表示した対象と指紋を既存の承認APIへ送る。Bは保留で、承認を送信しない。回答時のセッション・Origin・CSRF・対象SHA・計画の指紋の検査を満たす必要があり、分類結果や過去の計画了承は操作の認可を代替しない。コマンドは読むだけで、記号回答や承認を自動生成しない。

### 遅延有事

実行中の実装（light・standard・heavy別）と担当PCが引き受けた作業（種類別）を監視する。終了時刻が直近30日内の成功標本について、実装は最初のleaseから最初のPR作成まで、担当PC作業は引受けから終了までの時間を平均する。同じ区分に10件未満しかない場合や区分・時間を確かめられない場合は判定しない。

実行中の経過時間が該当平均の2倍以上になると遅延有事を登録し、15分の応答期限後に調査する。不具合と判定され、対象の正のIssue番号と稼働状態を確認できた場合だけ、原因の対策を高優先度で自動起票する。担当の引き継ぎは行わず、対応は既存の許可内の再試行と要対応への掲示に限る。直接PRが必要なら起票本文と要対応に残る。起票結果が確認できない場合は再投稿せず、[照合手順](slow-incident-recovery.md)に従う。

## 受付の窓口

NASの`~/.issue-desk/desk <名前.ts> [引数]`は、一意に確認した書き手と同じイメージ・ネットワークでチャットCLIを実行する。`deploy/nas/chat-local.ts`がHTTPの試行ごとに`intake admin ... cli-key issue`を呼ぶ。キーは32バイトの乱数、有効期限60秒で、受付のPostgreSQLにはSHA256だけを保存する。受付が一度だけ消費し、通信終了時にも未消費キーを回収する。Bearerへ自動で切り替えず、既存PCトークンを発行し直さない。

窓口は呼出しごとに稼働書き手の環境を読み、`ISSUE_DESK_APP_STORE`・`ISSUE_DESK_DATABASE_URL`・`PGHOST`・`PGUSER`・`PGDATABASE`・`PGPASSWORD`をホーム配下の権限600の一時env-fileで渡す。パスワードをコマンド引数やログへ出さず、成功・失敗・割込みの終了時にファイルを削除する。環境の読取失敗、不正値・重複・改行、PostgreSQL指定で接続先が未設定なら起動前に失敗する。`ISSUE_DESK_EXPECTED_APP_STORE`でadminでも受付と窓口の保存先を照合し、不一致や接続失敗の固定診断をCLIへ伝える。受付はPostgreSQL専用で、sqlite指定や切替記録のない保存先は使わない。

一時キー窓口は起動時に書き手が不在か接続を確認できない場合、最大180秒、原則1秒間隔で待つ。一方の色に接続できなくても、もう一方が書き手なら起動する。複数の書き手、コンテナ確認の失敗、不正応答は待たずに終了する。実行中の接続喪失または再試行可能な503の後は、`follow-issues.ts`、`list-issues.ts --duplicates`、`desk-get.ts GET`、`create-issue.ts --check` の許可された引数だけを再起動する。交代検出から180秒以内に最大3回再起動する。子が180秒以上稼働した後の切断は新しい交代として期限と回数を数え直す。見張りと下書き確認の元の期限は延長しない。再起動の期限や回数の上限では理由を表示して終了コード1で終了する。見張りの通常の期限到達で張り直しを案内する終了コード3とは異なり、必要なら窓口を改めて起動する。`--check-only`、送信を伴う呼出し、別接続先、再試行対象外経路は再起動しない。送信後の結果待ちで接続が失われた場合は、受付済み下書きIDと読むだけの `--check` を案内する。`intake.sh active`・`status`・`exec` は従来どおり即時判定する。送信を伴う呼出しは窓口を再起動しないが、交代中の要求は受付の色が保留して書き手へ渡し（[交代時の要求処理](#交代時の要求処理)）、未受理の印（`X-Issue-Desk-Not-Accepted: 1`）付きの503は `scripts/lib/desk-retry.ts` が試行ごとに新しい一時キーで送り直す。

読取専用の再試行可能なGETでは、一時キーの発行に失敗した場合も同じ上限内で再起動する。回収できなかったキーは発行から1分で失効する。見張り・確認の期限の起点は起動時の書き手待機が終わった後の秒単位の時刻で、最大1秒程度の端数がある。probeの健康応答が `ok=false` の場合は不正応答として終了し、接続できない場合の待機とは区別する。

NASの窓口は `stage-watch.ts`・`desk-ops.ts notice` と、`reply-issue.ts` の `--over-limit-statement`・`--implementation-limit-retry`・`--approval-question`・`--approval-answer` 付き呼び出しを `~/.issue-desk/desk-pc` のPCトークン接続へ振り分ける。それ以外の残存スクリプトは一時キーを使う。振り分け一覧は `deploy/nas/desk-pc-routes.json` に一元管理する。Skillへ移行した再試行・承認・ホスト操作・TODO保存/編集・クローズ依頼・PR作成/マージなどは、NASでは明示的に `sh ~/.issue-desk/desk-pc get|operation`、Ubuntuでは `~/.issue-desk/desk get|operation` を使う。PCトークン窓口が無い場合は実行せず失敗する。

NAS更新は稼働Serverのrevisionを確認し、配置先のGitから `~/.issue-desk/checkout/<revision>` へ写して `scripts-root` の1行目を切り替える。2行目には直前の向け先を残し、稼働版を確認できない場合や写しの作成に失敗した場合は以前の向け先を保持する。使用中の写しは削除しない。

この振り分けはNASの自動処理にも適用される。例えば `deploy/nas/update-remote-control-guard.sh` が窓口から送る `desk-ops.ts notice` も desk-pc を経由する。

汎用読取は `~/.issue-desk/desk desk-get.ts GET '/api/drafts?view=summary&limit=20'`。GET専用で、JSON出力は既定1 MiB、`--max-bytes` は最大16 MiB。経路の `security` で認証区分を確認する。NASの一時キーで読めないpcToken専用経路はPCトークン接続が必要で、自動切替しない。

Ubuntu PCの同じ窓口は、稼働WorkerイメージへIntakeの`scripts/`と`shared/`だけを読み取り専用で見せ、PCのK2とPCトークンでHTTPSの受付を呼ぶ。NAS専用の一時キー発行モジュールは見せない。`doctor|get|operation`はWorkerのGo製`desk`を呼ぶ。受付スクリプトはGiteaやDBを直接操作しない。

`--file`などに渡すファイルと作業ディレクトリはホーム配下に置く。窓口はホーム外へ解決される既存パスを拒否する。`follow-issues.ts --state` は未作成の場合もホーム配下へ解決される絶対パスを指定する。トークンは標準出力・引数・ログへ出さない。

## チャットの承認の証跡

利用者がチャットで承認した操作をAIが運用の代行を許したトークンで送るときは、承認の証跡として次の2つを必ず付ける。どちらかが欠けると受付（Server）は400で断る。Skillは送信前にも照合する。受付画面からの承認は対象外で、従来どおり。

- 利用者の発言の原文: 汎用 operation ではJSONの `statement`・`overLimitStatement`、マージCLIでは `--approval` にそのまま渡す。利用者が記号だけで答えたときは、見せた質問文と回答を組にしてJSONの発言へ記録する。残るCLIが対応するときは `--approval-question <見せた質問文>` と `--approval-answer <記号>` を渡す。推測・要約で作らない。
- 指示の日時: JSONの `instructionAt`（残るCLIでは `--instruction-at <日時>`）。AIは会話にある利用者のその発言の時刻を読み、UTCオフセット付きISO 8601（秒まで。例 `2026-11-11T11:58:00+09:00`）で渡す。未来の日時と7日より前の日時は断る。送った時刻やAIが決めた時刻で代えない。

| 経路 | Skill・窓口 | 受付API | 日時を記録する場所 |
| --- | --- | --- | --- |
| 最終承認 | issue-desk-issue-control Skillの最終承認 | `POST /api/comment`（`approve-final`） | ジョブの `finalApprovals[].instructionAt` |
| 削除の承認 | issue-desk-issue-control Skillの削除承認 | `POST /api/comment`（`approve-deletions`） | 承認の記録とIssue・PRの監査コメント「指示の日時」 |
| 権限変更の承認 | issue-desk-issue-control Skillの権限承認 | `POST /api/comment`（`approve-permissions`） | `permissionApproval` の承認記録と監査コメント「指示の日時」 |
| 上限超過の再試行・返信 | 再試行Skillの `overLimitStatement`・`reply-issue.ts --over-limit-statement` | `POST /api/comment`（`overLimitStatement`） | ジョブの `overLimitApprovals[].instructionAt` |
| 相談の続行・代理回答の取消・プロジェクト作成の同意 | issue-desk-issue-control Skillの相談承認 | 各 `continue`・`proxy-undo`・`approve` | 続行・取消・同意の記録の `instructionAt` |
| 承認付きマージ | merge-manual-pr Skillの汎用 operation | `POST /api/v1/requests`（`merge_manual` の `instructionAt`） | マージ依頼の内容 |
| 停止中のNASの入れ替え | なし | `POST /api/intake/force-handoff` | 監査記録の `instructionAt` |
| 許可の付与 | issue-desk-issue-control Skillの許可登録手順 | `POST /api/permission-grants` | JSONの `quote`・`statedAt` が必須 |

受付は発言・日時・経路（`chat`・`token`）・送信元PCを、それぞれの記録に残す。

## 許可付きのDB参照

受付のDBは [issue-desk-apiのDB照会手順](../skills/issue-desk-api/refs/db-query.md)から、汎用 operation で `POST /api/diagnostics/db-query` へ送り、結果（`columns`・`rows`・`truncated`）をJSONで表示する。送り直すのは、受付が処理に入る前に未受理の印（`x-issue-desk-not-accepted`）を付けて返した503のときだけで、ほかの失敗（400・403・409・504・印のない503・切断）は送り直さず終了コード1で終わる。応答が結果の形でないときも成功にしない。対象は `shared`（共有DB、スキーマ `public`）と `app`（アプリのDB、スキーマ `issue_desk_app_migration`）。画面セッションでは使えず、一時キーか運用の代行を許したPC別トークンで送る。加えて、対象に有効な期限付きの db-read の許可の付与が要る（恒久の許可では実行できない）。許可の登録から取り消しまでの手順は `issue-desk-issue-control` Skill の「DBを参照する（db-read）」に従う。

受付は許可を実行のたびに読み直し、SQLを検査してから、検索パスを `pg_catalog` 優先にした READ ONLY トランザクションで実行する。SQLは SELECT または WITH から始まる1文だけ（末尾の `;` とコメントは可）。書き込み・DDL・`SET`・`CAST`・`INTO`・`FOR` などの語、`::` の型変換、許可一覧にない演算子、許可一覧にない関数、`pg_` で始まる識別子と `information_schema`、別名による修飾（`j.status`）、対象外のスキーマの修飾は400で断る。修飾は対象のスキーマ名（`public.jobs` など）だけ使える。

上限は次のとおり。超えた照会は実行しないか、途中で打ち切る。受付は対象・`maxRows` の形、同時実行、許可の順に確かめてからSQLを検査するので、SQLの検査による400は対象に有効な許可があるときだけ返る。

| 項目 | 上限 | 超えたとき |
| --- | --- | --- |
| SQLの長さ | UTF-8で65536バイト | Skillで送信前にも照合する。受付は対象に有効な許可があれば400、無ければ許可の確認が先なので403 |
| 実行時間 | 5秒（ロック待ちは500ms、接続待ちを含む要求全体は6秒） | 504（ロック待ちの超過は400） |
| 行数 | `maxRows`（1〜1000、既定100） | `truncated.rows` が true |
| 応答の大きさ | 256KiB（262144バイト） | `truncated.bytes` が true。1行だけで超える行はその手前で打ち切る |
| 列 | 1〜1600列。型は真偽・整数・小数・文字列・日時・UUID・JSON のスカラーだけ | 400（複合型・record・bytea は不可） |
| 同時実行 | 全対象で1件 | 409 |

打ち切られた結果は全件ではない。条件を絞るか集計にして読み直す。503はDB接続か監査の保存が使えないときで、監査を保存できなかった照会の結果は返さない。

### 資格情報の除外

除外は `server/internal/adminapi/db_query_guard.go` の一覧で決まり、ここの記述はその写し。SQLの字句（引用符付きを含む識別子）と結果の列名を名前で照合するため、別名・`*`・行全体・JSONの中身を経由しても読めないよう、資格情報を持つ表は表ごと除外している。

- 表ごと除外: `settings`（セッション・CSRF・PCの資格情報を含む）・`host_image_tokens`・`ssh_tickets`・`api_tokens`・`api_token_grants`・`cli_keys`・`temporary_code_records`。SQLのどこかにこの名前の識別子があれば断る。
- 名前で除外する列: `requested_token`・`hash`・`password`・`secret`・`credential`・`csrf`・`session`。SQLのどこかにこの名前の識別子があれば断る。
- 結果の列名: `token`・`hash`・`secret`・`key`・`password`・`credential`・`csrf`・`session` のどれかを含む列名（大文字小文字を区別しない）の結果は返さない。
- 資格情報ではないと確かめた列: 共有DBの `usage_rows.key`・`usage_limit_rows.key`・`fixed_test_usage.key`・`runner_log_lines.key`、アプリのDBの `attention_cases.key`・`job_filings.key`・`stall_fixes.key`・`draft_withdrawals.token_name`・`topic_link_removals.token_name`。識別子やラベルで、認証には使わない。結果の列名の検査に掛かるので、`SELECT key AS k` のように別名を付けて読む。

列名に上の8語のどれかを含む列をスキーマへ足すときは、除外するか、資格情報ではない列の一覧に入れるかを決める。決めていない列があると、出荷スキーマの全列を照合するGoテスト（`TestDBQuerySecrets` の inventory）が落ちる。

### 監査

認証を通ってこの経路の処理に届いた要求は、実行・拒否（運用の代行なし・許可なしの403、検査で断った400、同時実行の409、DBが使えない503、時間切れの504）のどちらも `admin_audit` に操作 `db-query` として1件残る。処理に届く前に返る応答は残らない: 認証の失敗（401など）、取り決めの版の不一致の409（`CONTRACT_MISMATCH`）、受付の入れ替え・書き手待ちの未受理の503。監査の保存そのものに失敗したときは503を返し、結果も監査も残らない。残すのは日時・送信者（actor）・許可ID・対象・送られたSQLの全文・HTTPの結果で、結果の値とPostgreSQLのエラーの詳細は保存しない。65536バイトを超えるSQLは先頭65536バイト以内と、元のバイト数（`sqlBytes`）・全文のSHA-256（`sqlSha256`）を残す。対象が `shared`・`app` 以外の要求は、対象を空で残す。SQLの全文が残るので、SQLに秘密の値を書かない。

### 必須検証の固定入口

Claude Codeのガードには、固定テストを実行する `verify` と、検証記録を点検する `verify-store` がある。

```sh
bash ~/.claude/hooks/guard-gitea.sh verify
```

- 対応表: `git remote get-url origin` から特定したリポジトリが `mofua-suki/issue-desk-intake` なら `sh scripts/verify.sh`、`mofua-suki/issue-desk-worker` なら `go test ./...`・`go vet ./...`・`gofmt -l .` の出力が空であることの3つを、作業場所の最上位で実行する。すべて成功したときだけ合格。対応表に無いリポジトリは固定の理由で拒否する。Worker用の対応表もこのガードに置き、Workerの通常の公開経路（Workerリポジトリ側の検証と公開）は変えない。
- 引数は受け付けない。検証コマンドの指定、結果の申告、フラグを付けた呼び出しは何も実行せず拒否する。標準入力は読まない。変更と無関係な失敗、修正前からある失敗も不合格にする。
- 検証のコマンドと、作業場所・originを読む `git` は、呼び出し元の環境値を引き継がずに実行する（`/usr/bin/env -i`、無ければ `/bin/env -i`）。渡すのは `HOME`・`PATH`・`LANG`・`TMPDIR` の4つだけで、設定されていないものは渡さない。それ以外（`GO`・`GOFLAGS`・`GOOS`・`CGO_ENABLED`・`XDG_CONFIG_HOME`・`NODE_OPTIONS`・`GIT_DIR`・`GIT_CONFIG_COUNT`・`LD_PRELOAD`・`ISSUE_DESK_TEST_POSTGRES_DSN` など、名前を問わない）は検証に届かない。このため `GOFLAGS=-p=2` のような負荷の調整もこの入口では効かない。`go`・`gofmt` は `scripts/verify.sh` と同じく `~/.local/bin` にあればそれを使い、無ければ渡した `PATH` から探す。
- ガード自身のbashの起動に作用する設定を見つけたら、検証を実行せず実行不能にする。対象は、環境に設定された `BASH_ENV`（ファイルの有無を問わない）、環境から渡された `SHELLOPTS`・`BASHOPTS`、環境から取り込まれたシェル関数（`BASH_FUNC_名前%%`。ガードと同じ名前のものを含む）。
- なお残る経路（この入口では防げない）: `HOME`・`PATH` はそのまま渡すので、そこに置かれた実行ファイル（`sh`・`git`・`go`・`gofmt`・`node` など）や `~/.gitconfig`・`~/.config/go/env` などの設定の中身は確かめない。ガードのbashが起動する時点で働くもの（`BASH_ENV` のファイルの実行、関数の取り込み、`LD_PRELOAD` などbash自身への作用）はスクリプトが動く前に効くため、上の検出を差し替える細工（`BASH_ENV` のファイルが自分の設定を消す、検出に使う `builtin`・`declare` を本物そっくりに差し替える）までは防げない。`SHELLOPTS=noexec` を渡すとbashは何も実行せず、何も表示しないまま終了コード0で終わる。合格とみなすのは終了コード0かつ「必須検証（段1）: 合格」の行が出たときだけにする。確実に避けるには、呼び出す側が `env -i HOME="$HOME" PATH="$PATH" LANG="$LANG" TMPDIR="${TMPDIR:-/tmp}" bash ~/.claude/hooks/guard-gitea.sh verify` のように環境を空にして起動する。
- 終了コードは 0=合格、1=不合格、2=拒否（引数あり・対応表に無い）、3=実行不能（起動環境に上の設定がある、`env` が無い、Gitの作業場所やoriginを確認できない、必要なコマンド・`scripts/verify.sh` が無い、検証の記録を開始・保存できない、後から始まった検証がある、中断された）。
- 不合格のときは、失敗した固定の検証コマンドと終了コード、失敗テスト名を最大10件表示する。名前は長さと文字の種類を限り、秘密らしい長い英数字の並びを含むものは表示せず件数だけを示す。安全な名前を1件も取り出せないときは、失敗した検証コマンドと固定の理由だけを表示する。検証の出力そのものは表示せず、入力・検証の出力をコードとして評価しない。

### 必須検証の記録とロック

作業場所で `verify-store` を実行すると、保存先・記録・ロックを点検できる。固定テストや既存記録の変更は行わない。

```sh
bash ~/.claude/hooks/guard-gitea.sh verify-store
```

- 点検の内容: 保存先を確かめ（無ければ作る）、ロックを取り、既存の記録があれば安全に読めることを確かめ、点検用の記録（`probe`）を書いて読み戻して消し、ロックを解放する。既存の記録（`record`）は読むだけで書き換えない。引数は受け付けず（保存先・記録の中身・結果は指定できない）、標準入力は読まない。起動環境の検出、環境値の除去、リポジトリの特定と対応表は `verify` と同じ。
- 保存先: `<基点>/guard-gitea/verify/<作業場所の最上位のパスの % を %25、/ を %2F に置き換えた名前>/`。作業場所ごとに1つ。
- 基点の選び方: `id -u` の番号で決まる `/run/user/<番号>` が、リンクでないディレクトリ・実行者の所有・権限ちょうど700なら、そこを基点にする。そうでなければ（無い・リンク・所有や権限が違う・`id` が使えない）`$HOME/.local/state` を基点にする。`XDG_RUNTIME_DIR` などの環境値からは選ばない。`/run/user` の基点は再起動やログアウトで消え、消えた記録は「記録なし」として扱う（成功にはならない）。
- 保存先の検査: どちらの基点でも同じで、`guard-gitea` 以下のディレクトリは、リンクでないこと・実行者の所有・権限700を、記録は、リンクでないこと・通常のファイル・実行者の所有・権限600・ハードリンクなしを、使うたびに確かめる。`$HOME/.local/state` を基点にするときは、`.local`・`state` を1段ずつリンクでないディレクトリと確かめながら作り、途中がリンクなら何も作らずに実行不能にする。基点の `state` が実行者の所有でないときも使わない。ACL付きで権限700・600にならない場所（NASの `/home` など）が基点になったときは、緩めずに実行不能にする。
- 記録の形: 7行固定の版3（`guard-gitea-verify 3`、`state=`、`generation=`、`repo=`、`run=`、`identity=`、`results=`）。`run=` は記録を書いた実行の識別子（32桁の小文字の16進）。`identity=` は検証した対象の同一性の要約（40桁か64桁の小文字の16進。まだ読めていないときは `-`）、`results=` は実行した検証ごとの `名前:終了コード` をカンマで並べたもの（実行できなかった検証は `名前:x`、1つも実行していないときは `-`。100文字まで）。`passed` は、`identity=` が要約で、`results=` のすべてが `:0` のときだけ正しい形とする。`read` と正規表現だけで読み、記録・入力・パスの中身をコードとして評価しない。行の数や値が決まった形でなければ失敗にする。値は実行時のロケールに依らず ASCII の文字だけを受け付ける（全角の数字などは通さない）。正規の7行が取り得る大きさ（491バイト）を超える記録と、読んだ行のバイト数がファイルの大きさと合わない記録（NUL入りなど）も失敗にする。書くときは同じ保存先の一時ファイルへ書いてから置き換え、読み戻して一致を確かめる。
- 旧い版の記録: 版1（4行、`guard-gitea-verify 1`。識別子なし）と版2（5行、`guard-gitea-verify 2`。同一性と結果なし）は、形が正しければ読めるが、どの実行の記録とも一致させず、合格としても扱わない。`verify` の開始時・無効化時に版3で上書きされ、旧い版の `passed` が合格として残ることはない（`verify-store` は読むだけで書き換えない）。段4で記録を読むときは版3以外を合格にしないこと。版1・版2・版3のどれでもない記録は安全に読めない記録として失敗にする。
- 実行の識別子: 実行ごとに bash の `SRANDOM`（bash 5.1 以降）からスクリプトの中で作る。環境値からは読まず、引数・標準入力・環境値で指定できない。bash が 5.1 より古い、または乱数を得られないときは、記録を書けないので実行不能にする。
- ロック: 保存先の `lock` ディレクトリ（`mkdir` の成否で排他）で、中の `owner` に持ち主のプロセス番号を書く。約2秒待っても取れなければ失敗にする。残ったロックを自動では奪わない（持ち主が生きているかを安全に判定できないため）。`INT`・`TERM`・`HUP` の中断では、`verify` も `verify-store` も自分が取ったロック（`owner` が自分）だけを解放してから終わり、他者のロックには触れない。基本の道具（`id`・`ls`・`mkdir`・`mv`・`rm`・`rmdir`・`sleep`）は中断を無視して動かすので、端末の Ctrl+C のようにプロセスの組の全員へ合図が届いても、ロックの解放や記録の置き換えが途中で止まらず、ロックを残さない（中断はガード自身が受けて後始末する）。`verify-store` は中断されても点検の片付け（`probe` の削除とロックの解放）まで進めてから、終了コード3の「中断された」で終わる。後始末なしの強制終了（`KILL`・電源断）で残ったときは、ほかの検証や点検が動いていないことを確かめてから保存先の `lock` を消す。
- 失敗の扱い: 不正な保存先、所有・権限の不備、リンク、読取不能、書込不能、ロックを取れないときは、固定の理由を1つ表示して実行不能にし、成功として扱わない。記録が無いことと、記録を安全に読めないことは区別する（後者は失敗）。
- 終了コードは 0=点検に成功、2=拒否（引数あり・対応表に無い）、3=実行不能。成功とみなすのは終了コード0かつ「必須検証の記録（段2前半）: 点検に成功」の行が出たときだけ。
- 使う道具は bash と `git`・`env`・`id`・`ls`・`mkdir`・`mv`・`rm`・`rmdir`・`sleep`。追加のhelperは配らない。

- 保存先は `id -u` の番号と `HOME` で決まり、`HOME`・`PATH` に置かれた道具の中身は確かめない。権限と所有者は `ls -ldn` の表示で読むため、権限700・600を表現できないファイルシステムでは点検も `verify` も実行不能になる。

### 必須検証の記録の無効化と世代管理

上の `verify` は、検証の開始と終了で前の節の記録（`record`）を書き換える。

- 開始時の無効化: 検証を1つも実行する前に、ロックを取って記録を `state=running`・世代（`generation`）を1つ進めた番号に書き換える（記録が無ければ世代1）。旧い成功（`passed`）はこの時点で消える。書き換えられなければ（不正な保存先、所有・権限の不備、リンク、既存の記録を安全に読めない、書き込めない、ロックを取れない、世代を進められない）検証を実行せず、終了コード3の実行不能にする。
- 終了時の保存: ロックを取り、記録が「`running`・自分の世代・同じ repo・自分の実行の識別子」のすべてに一致するときだけ、結果を同じ世代で保存する（すべて成功=`passed`、失敗=`failed`、必要なコマンドやファイルが無い=`invalid`）。後から始まった検証があると世代と識別子が変わっているので、先に始まって遅れて終わった検証は結果を保存できず、成功していても終了コード3の実行不能になる。最新に始めた検証だけが結果を保存できる。記録が消えて（`/run/user` の基点はログアウトで消える）世代が同じ番号に戻っても、識別子が違うので、消える前に始まった検証は結果を保存できない。
- 合格の条件: 検証がすべて成功し、検証の前後で対象が同じと確かめられ（次の節）、かつ結果を保存できたときだけ終了コード0で「必須検証（段1）: 合格 repo=…。結果を世代 N として記録し、検証の前後で対象が同じことを確かめた。…」の行を出す。成功しても保存できなければ合格にしない。失敗・実行不能の結果を保存できないときは、元の終了コードのまま「記録: この検証の結果を保存できない（理由）。」の行を足す（記録は `running` のまま残り、成功にはならない）。
- 中断: `INT`・`TERM`・`HUP` を受けると、実行中の検証コマンドやロック中の書き換えが終わった後に後始末をし、自分のロックを残さず、終了コード3で終わる（検証コマンドが成功していても合格にしない）。後始末は中断された時点で変わる。(1) 開始の書き換えの後: 記録が自分の実行のもの（世代・repo・識別子が一致）なら、状態を問わず `invalid` にする。成功を保存した直後に中断が届いたときも `passed` を残さない。無効にできなければ「この検証の記録を無効にできない（理由）」と表示する。(2) 作業場所の確認の後、開始の書き換えの前: 世代と識別子が決まっていないので、両方の基点の既存の記録の無効化を試み、できたときは「旧い記録を無効にした」、できなかったときは「旧い記録を無効にできない（理由）」と表示する（できなかったのに無効と表示しない）。(3) 作業場所の確認の前: 記録には触れず「検証を始めていない」と表示する。後始末なしの強制終了（`KILL`・電源断）では記録が `running` のまま残る。`running` は成功ではなく、次の `verify` は世代を進めて始められる。ロックを持った瞬間に強制終了されたときは `lock` が残り、前の節の手順で消すまで `verify` は実行不能になる。
- 検証を始められない場合の旧い成功: originからリポジトリを特定できない・対応表に無いときは、その作業場所の記録があれば `invalid` にしてから終わる（保存先は作らない。無効にできなければ「記録: この作業場所の旧い記録を無効にできない（理由）。」の行を足す）。引数付きの呼び出し・起動環境の検出・`env` が無い・Gitの作業場所を確認できないときは、保存先に触れずに拒否・実行不能で終わる（検証を始めていないので、記録は前のまま）。
- 基点の両側の扱い: 基点は実行のたびに選ぶので、`/run/user/<番号>` を使えるときと使えないときで保存先が切り替わり得る。`verify` は開始時に、今の基点でない側（`/run/user/<bashの実行者番号>` と `$HOME/.local/state` のもう一方）の同じ作業場所の保存先も見て、記録があれば `invalid`（世代を1つ進める）にする。成功を保存する直前にも同じことをもう一度行う。今の基点でない側の記録を無効にできないとき（安全に読めない・保存先の所有や権限の不備・ロックを取れない）は、検証を始めない、または成功を合格にしない。このため、基点が切り替わっても、他方に残った旧い成功が生き返ることはなく、別々の基点を選んだ検証が並行しても両方の側に成功が残ることはない。今の基点でない側に保存先が無ければ何も作らない。
- 記録・標準入力・環境値の中身はコードとして評価しない。記録は検証の結果だけで決まり、引数・標準入力・環境値で `state`・世代・識別子を指定することはできない。
- `HOME` が変わった場合: `$HOME/.local/state` 側の保存先は `HOME` で決まるので、`HOME` を変えて実行すると別の保存先になり、元の `HOME` 側に残った記録は両側の無効化の対象外になる（段4で、送信時の保存先にある記録だけを読むことで扱う）。
- テストの前提: 基点の切り替わりのテスト3件（`test/guard-gitea.test.ts` の「基点の切り替わり:」で始まるもの）は、実機の `/run/user/<番号>` が実行者の所有・権限700で在る筐体でだけ走り、無い環境では skip になる。その環境では両側の無効化が検査されていないので、`/run/user/<番号>` のある筐体（NASなど）での結果で確かめる。

### 必須検証の同一性の記録と検証後の照合

`verify` は、何を検証したか（同一性）を記録に持たせ、検証が終わった時点で同じ対象かを確かめる。

- 同一性に含めるもの: リポジトリ（originから特定した `owner/repo`）、作業場所の最上位のパス、管理場所（Gitのディレクトリと、作業場所どうしで共有するGitのディレクトリの絶対パス）、先頭コミット（`HEAD` のコミットID）、ブランチ（`HEAD` が指す `refs/heads/…`。ブランチを指していなければ `(detached)`）、送信先（originの取得用URLと、送信用URLのすべて）、検証定義（対応表の検証名と固定コマンド。Intakeは `scripts/verify.sh` の内容のIDも含む）、フック（実行中のガード自身の内容のID）、内容（先頭コミットに作業場所の今の状態を重ねた木のID。追跡ファイルの変更・削除と、無視されていない未追跡ファイルを含む）。各検証の結果は記録の `results=` に持つ。
- 同一性に含めないもの: `.gitignore` などで無視されているファイル（ビルド成果物・依存物・`.tmp/` など）、ステージ済みか未ステージかの違い（中身が同じなら同じ内容とみなす）、Gitの `hooks` ディレクトリや設定ファイルの中身、`HOME`・`PATH` に置かれた道具の中身、ファイルの時刻。
- 記録の持ち方: 上の項目を決まった順の文にし、`git hash-object` で要約した値だけを記録の `identity=` に持つ（項目ごとの値は記録に残さない）。後から比べるときは、同じ手順で作り直した要約と比べる。
- 内容の読み方: 保存先の中の一時のインデックス（`identity.<プロセス番号>`）を使って `git read-tree HEAD`・`git add -A`・`git write-tree` で木を作る。作業場所のインデックス（何がステージ済みか）と作業場所のファイルは変えない。一時のインデックスは読めたかどうかに依らず消し、消せなければ失敗にする。同じ名前の物（本体・`.lock`）が前から在るときは、自分が置いた物ではないので使わず、消さずに失敗にする。木を作るときにGitの保管庫へ内容の控え（参照されないオブジェクト）が増えることがある。`git` は検証と同じく呼び出し元の環境値を引き継がずに呼ぶ。
- 開始時: 開始の書き換え（`running`。旧い成功はここで消える）の後、検証を1つも実行する前に同一性を読む。読めない・要約できないとき（管理場所・先頭コミット・ブランチ・送信先・検証定義・フック・内容のどれかを読めない、コミットが1つも無い、一時のインデックスを置けない・消せない）は、検証を実行せず、記録を `invalid` にして終了コード3の「検証の対象の同一性を記録できない（理由）」で終わる。
- 検証後の照合: 検証がすべて成功したら、成功を保存する前に同一性を読み直して開始時と比べる。違えば「検証の間に対象が変わった（変わった項目の名前）」、読み直せなければ「検証の後の同一性を確かめられない（理由）」と表示し、成功していても合格にせず、記録を `invalid` にして終了コード3で終わる。表示するのは変わった項目の名前（リポジトリ・作業場所・管理場所・先頭コミット・ブランチ・送信先・検証定義・フック・内容）だけで、値は表示しない。比べるのは開始時と終了時の2点で、途中で変わって元へ戻ったものは見つけない。
- 検証のスクリプトの形: `scripts/verify.sh` がリンク・通常のファイルでないときは、無いときと同じく実行せず実行不能にし、検証定義には「無い」と記録する（リンク先を実行すると、その中身が検証定義にも内容にも入らないため）。実行するかどうかと検証定義に含めるかどうかは同じ判定を使う。Workerの検証（`go`・`gofmt`）は作業場所のスクリプトを実行しない。
- 失敗・実行不能の記録: 検証が失敗・実行不能のときは照合せず、開始時の同一性と各検証の結果を持つ `failed`・`invalid` を保存する（成功にはならない）。
- 先頭がブランチを指していない状態と送信用URLが複数ある状態は同一性の一部として記録し、固定テストの開始は許可する。

検証記録とpushの条件

- `verify` は開始と終了時の対象を照合する。合格後の編集・コミット・枝の切替で記録は更新されない。検証時に未コミットの変更を含める場合、先頭コミットと作業内容を別々に記録する。入れ子のリポジトリとサブモジュールでは先頭コミットを記録する。
- Claude CodeのPreToolUseフックは検証記録を参照せず、pushは既存の送信規則で判定する。Codexにはこのフックが掛からない。
- NASの更新とUbuntuの `rc-update.sh` はガードを配布する。フックはClaude CodeのPreToolUseに登録済みの環境で動く。`verify` と `verify-store` は未登録の環境でも実行できる。

## Ubuntuの初回導入と更新

Ubuntu本人のBashで次の1行を実行する。稼働Intakeの固定コミットから導入入口を取得する。OSの導入・ログイン・イメージ取得を含むため所要時間はネットワークと認証待ちによる。途中でCtrl+Cを押さない。

```sh
ssh user@192.168.0.10 'sh ~/Workspace/issue-desk-intake/deploy/clients/bootstrap-entry.sh' > ~/bootstrap-ubuntu.sh && bash ~/bootstrap-ubuntu.sh
```

導入はOS・Docker・Tailscale・ホスト名を確かめ、担当表とfleetをIntakeから読む。Workerの望む版はNASのGo管理CLIから読み、その固定コミットの`deploy/`だけをWorker checkoutから取得する。K2はworkerId・serverUrl・serverTokenFileの3項目で、blueへ配置する。取得したWorkerのcompose.yamlが`issue-desk-worker-state-green`を参照する場合はgreenにも配置する。

PCトークンの発行・失効はNASの管理CLIを使う。同名トークンが既に有効なら自動で失効せず、本人の明示入力を待つ。監視用Giteaトークンは既存のものを非表示入力で受け取り、Workerの`token-place`で対象のstateボリュームの本人照合を済ませてから配置する。対象はblueと、compose.yamlが`issue-desk-worker-state-green`を参照する場合のgreenで、対象すべての既存トークンが本人照合に合格すれば入力し直さない。gitUser用の管理トークンを監視用トークンとして配らない。

既存PCは受付で引き取りを止め、有効な停止期限・新しいheartbeat・restartSafe・実装中0・公開中0を確認してから局所更新する。起動後にWorkerの自己検査と新しいreadyのheartbeatを確認してから再開する。hostdはWorkerの局所installerで設置し、既存のtokenとregistry-passwordを保持する。

## NASの依頼別使用量レポート

依頼別使用量は専用Skill `skills/usage-per-issue/SKILL.md` に従い、NAS受付コンテナ内のGo管理CLIで読む。利用者の依頼と直接CLIの実行許可を確認し、許可が未確認なら実行せず理由を伝え、権限変更や別経路での回避もしない。共有DBとアプリ用PostgreSQLへの接続が整った環境で、設定値や資格情報を出さない。

```sh
/usr/local/bin/intake admin --config /state/config.local.json --application-dir /app usage-per-issue report --from 2026-11-01 --to 2026-11-30 --repo owner/repo --format json --population all
```

`--from`・`--to` は必須の実在する日本時間の日付で終了日を含む1〜92日。`--repo` は任意の `owner/repo`、`--format` は `table`・`json`・`both`（既定）、`--population` は `merged`（既定）・`all`。`all` は未マージを含むJSON詳細を追加し、表や通常集計は変えない。各引数は高々1回、`--config` と `--application-dir` は `admin` の直後に指定する。CLIは `--sqlite` を受け付けない。終了状態、期間、件数、欠測・読めない行と分割相談の帰属を確認し、失敗や不明を成功・ゼロと扱わない。JSON詳細と通常集計の違いを含む確認手順はSkillを参照する。

NASのチャットでは、許可の付与 `nas-claude-rule`／`usage-per-issue`（`deploy/nas/permission-grant-rules.json`）が、ホストから `sh ~/Workspace/issue-desk-worker/deploy/nas/intake.sh exec -T /usr/local/bin/intake admin --config /state/config.local.json --application-dir /app usage-per-issue report --from …` を呼ぶ形だけを許す。`--config` と `--application-dir` は固定で、`report --from` より前を変えた呼び出しは許可されない。有効な許可が無ければレポートを実行しない。

NASの共有DB接続環境変数を使用し、PostgreSQLは読み取り専用のrepeatable-readトランザクション、下書きはアプリ用のPostgreSQL（`issue_desk_app_migration`）から読む。日本時間の指定終了日を含む1〜92日間にマージされた依頼を選び、起票前の相談の使用量は下書きの最初の起票先へ集約する。マージ後の使用量は含めず、分割相談の帰属件数・欠測・読めない行を区別する。下書き本文・資格情報は返さない。非NASのHTTPチャット配布にはこのDB読取入口を含めない。

NASのWorker配布資産は`~/.local/share/issue-desk/worker.git`の読取用bare cloneから取得する。導入時に`trunk`をfetchし、配布で指定されたWorkerの固定コミットから`deploy/`をarchiveする。Server/Clientの作業ツリーとWorkerの配布資産を混ぜない。

## 明示終了API

利用者が対象の終了を明示したときだけ照合し、終了する。NASでは `sh ~/.issue-desk/desk-pc operation`、Ubuntuでは `~/.issue-desk/desk operation` を使う。対象は `draft:ID|issue:owner/repo#番号|attention:ID|stall:ID` の形式。attentionは `attention:<key>` と `attention:attention:<key>` の両方を受け付け、応答と保存では後者にそろえる。NASでの照合例：

```sh
printf '%s' '{"target":"issue:owner/repo#12"}' | sh ~/.issue-desk/desk-pc operation --method POST --path /api/desk-cleanup/inspect --body-file -
```

終了する場合は同じ窓口でPOST `/api/desk-cleanup/close` にJSONを送り、照合で返った同じ `target` と `fingerprint`、理由 `reason`、利用者の指示原文 `userStatement` を指定する。JSONは適切にエスケープして `--body-file` で渡す。終了記録はGET `/api/desk-cleanup/archive` で読む。APIには画面認証または運用代行トークンが必要で、使い捨てキー・hostd資格情報は拒否する。窓口からの操作には運用代行トークンを使う。

相談は子の状態と関連Issueの全履歴を照合し、処理中・関連Issue未終了・対象変更なら409。起票結果不明から新規投稿や再試行はしない。通知の元状態は削除せず確認した内容だけを記録し、理由・詳細が変われば再表示する。時刻更新だけでは再表示しない。既存状態を自動で終了させない。閉じていて状態が失敗のIssue、または状態が完了で未了の受入確認があるIssueを明示終了した場合は、対象と指紋が一致する間、停止中から終了履歴へ移す。結果と受入確認の記録は保持する。

## 相談への回答

`--check <下書きID>` で質問と版を読み、以前読んだ質問への回答には `--draft <下書きID> --expect-revision <読んだ版> --text <回答>` を使う。版を省略すると送信直前にGETした版を使うが、そのGETより前の変更は検出できない。409の場合は表示された理由と最新質問を確認し、会話を読み直して回答を作り直す。最新質問を取得できなければ `--check` で確認する。版を更新した回答の自動再送はしない。

新規相談・回答と `--check` は thinking・auto_ready・submitting の間、指定期限まで結果を読み続ける。質問、hold確定待ち、予算停止、引継ぎでは待機を終える。最後の下書き読取後は、共通番号・題名や分割した子の補助読取に少なくとも5秒の猶予を設ける。起票失敗は原因と返された操作を表示し終了コード1とする。分割では子ごとの結果も確認する。処理中に期限を迎えた場合は終了コード0だが結果は未確認で、送り直さず `--check` で確認する。接続喪失で確認を打ち切った場合は終了コード2。起票結果不明も送り直さず照合する。

## 交代時の要求処理

更新はホストから実行する。待機色のDB接続・静的ファイルを確認し、実行中の処理が終わってから書き手を交代する。入口の確認に失敗したら旧色へ戻す。交代の間に届いた要求は、できるだけ失敗にせず書き手へ届ける。受け付けられない色（待機中、または交代で受付を閉じた後）は要求を業務処理へ渡さず最大120秒保留し、書き手になった色（`ISSUE_DESK_PEER_URL` の相手、または自色）へ1回だけ渡す。保留の期限・自色の停止で渡せなかった要求は `X-Issue-Desk-Not-Accepted: 1` 付きの503になり、チャットのスクリプト（`scripts/lib/desk-retry.ts`）は同じ内容を5秒間隔で送り直し、最初の未受理の応答から5分（または60回）を過ぎた応答で打ち切る（最後の1回が受付で保留された分だけ延びる）。保留するのは本文が1MiB以下の要求で、依頼側が切断した要求は渡さない。相手の色が交代の途中（受付を閉じたが書き手のまま）のときは保留されず未受理の503になる。旧色を止めるとき、保留中の読取は最大10秒間書き手を待つ。渡した後の読取（イベントの購読を含む）と `/next` で終わる書き込みの長い待ち（`jobs/next`）は最大10秒待ってから切る（依頼側が入口から繋ぎ直す）。ほかの書き込みは、書き手だった色なら停止の期限（45秒）まで終わるのを待つ（書き手にならずに止まる待機色はすぐ切る）。この印の無い失敗（渡した後の応答喪失の502など）は届いたか不明なので、送信IDで照合できる経路だけ送り直す。NASの一時キーは保留を始めるときに消費し、渡す直前に1回限りの引換キー（`X-Issue-Desk-Relay-Key`、共有DBに1分）へ置き換える。`ISSUE_DESK_PEER_URL` が無い色は保留せず503を返す。`deploy/nas/intake.sh status`で一意の稼働色とrevisionを確認できる。

相談の静止（Quiesce）は、新しいTurnと再試行を止める。既に始まったTurnが自動起票へ進む場合は、Submitと結果の保存まで待ってから交代する。待機の期限だけを取り消しても、進行中のTurnやSubmitは取り消さない。

交代に失敗するとログに `交代に失敗しました: handoff stage=... operation=... class=... pending=...` が出る。旧色はリースと開始停止の柵を保持し続ける。資源解放に失敗した場合も資源は既に閉じられていることがあるため、そのまま業務を再開しない。通常停止が先に資源を解放した場合も、その解放結果を交代で共有し、失敗ならリースを返さない。段2以降では業務要求が503になっても `/healthz` の role は active のままになり得る。自動で再試行しないため、配置処理が停止した場合や手動でSIGUSR2を送った場合は、配置操作が動作中でないことと稼働色を `deploy/nas/intake.sh status` で確認する。新色があれば停止してから、旧色のコンテナを `docker stop`（通常のSIGTERM停止）し、停止完了後に `docker start` する。旧色のhealthと入口からの業務応答を確認し、復旧しない場合はログの stage・operation・class・pending とDB接続を調べる。書き手が複数いる状態では操作を続けない。

交代時のAI失敗通知は、旧色で予約済みの送信と結果の保存を待ってから引き継ぐ。通知停止後に旧色で検知した失敗は未通知のまま保存され、要対応には残る。新色は記録の読み込みだけでは通知せず、同じ範囲で次の失敗を検知したときに通知する。交代後は要対応（`node scripts/desk-alerts.ts`）も確認し、次の失敗がなければ自動通知を待たずに内容を確認する。

## 新規相談の再送

新規相談では初回送信前に「送信ID」を表示する。POSTの応答を失った場合は、表示されたIDを `--send-id <ID>` に指定し、同じ接続先・送り手・本文・すべての指定値で再実行する。標準入力や `--file` の場合も元と同じ本文を渡す。受付済みなら同じ受領を照合して結果を待ち、異なる内容なら受付が拒否する。下書きIDを受け取った後は送り直さず `--check <下書きID>` で確認する。

「受領の内容が一致しません」と出たら、送信IDが初回に表示されたものか、接続先・送り手・本文・引数が元と同じかを確かめる。下書きIDが分かる場合は `--check <下書きID>` で読むだけの確認をする。この表示は取得した受領情報と送信IDを照合できなかったことを示し、本文の一致を判定した結果ではない。受領確認済みでも、再送時の本文・引数は受付が別途照合する。

## 起票後の見張り

受付は保存されたジョブを周期的に追跡し、停止・停滞や判断待ちを要対応への通知で知らせる。通常の完了は対象PRのマージを確認し、明示された取り下げは別の終了として扱う。確認できない終了は未確認のまま残す。通知予約は共有DBに保存し、送信に失敗した事象は次の周期に再送する。送信成功後は同じ事象を再送しない。一部の送信先だけ成功した場合や送信成功後の記録前に停止した場合は、既に届いた送信先にも再送されることがある。自動復旧には既存の承認と上限が適用される。チャットでは `scripts/follow-issues.ts` でも依頼を見張れる。

Codex向けのローカル入口は `node scripts/codex-issue-watch-deliver.ts --registration <登録ファイルの絶対パス> --notification-id <通知ID> --conversation-id <会話ID> --target <draft:下書きID または desk:共通番号> --state <held|decision|failed|completed>`。登録ファイルは同一ユーザー所有で他ユーザーから読書きできない通常ファイルとし、JSONに `host`、`conversationId`、`socket`、`journal`、`codexVersion` を指定する。`socket` は同一ユーザー所有のUnixソケットの絶対パス、`journal` は同一ユーザー所有で他ユーザーからアクセスできないディレクトリの絶対パスとする。現在の対応対象はCodex 0.171.0。登録の作成と維持は呼び出し側が行う。

`delivered` は対象会話の履歴に同一通知の追跡システム由来の出力が確認できた場合に返る。`busy`・`offline`・`unsupported`・`unknown` は未配信として保持し、`invalid` は入力または登録を確認する。送信前に通知IDと会話IDの組を記録するため、応答消失や待ち行列入りで `unknown` となった場合は同じIDで再実行して履歴を照合し、確認できないまま再送しない。記録を消して再送すると二重配信のおそれがある。`turn/start` の待ち行列入りは新規ターンの開始を意味しない。後続の実機確認は対象会話と操作の個別許可を確認し、保留通知1件と同じ会話での受付詳細確認開始を証跡で照合する。

NASのCodexは起票前の私有記録を受付の受領と照合し、下書きと分割子の対応から共通番号を追う。通知対象は受付の一覧APIが返す画面の「要対応」「停止中」。通常の依存待ちは通知の対象外。送達直前にも対象と分類を読み直し、読取失敗時は未確認のまま次回に持ち越す。端末が応答できない場合は既存の要対応に未配信を出す。

元会話に「Issue Desk 追跡通知」が届いたら、その回に対象の詳細を読み、停止や保留の理由を調べる。許可済みの対処を送ったら受付の送信IDを照合する。利用者の判断が必要なら受付の具体的な質問や最終承認の対象を提示する。明示的な停止、操作の上限、個別承認の条件に従う。元会話で `node scripts/codex-issue-watch.ts record <通知ID> <draft:下書きID または desk:共通番号> read` を実行して調査を記録できる。対処を送った場合は `read` の代わりに `operation <受付の送信ID>`、判断を求めた場合は `waiting <question または 承認ID@headSHA>` を使う。通知の送達と対処の記録は独立して保持し、対象のPRマージまたは明示的な取下げを確認するまで巡回する。

### NASの定期巡回

NASの更新が既存のユーザーsystemdへ `issue-desk-codex-watch.timer` と対応するサービスを配布する。サービスはNAS本体の `~/.local/bin/node` を使い、巡回の終了から約1分後に次を起動する。遅い受付照会が後続を塞がないよう、登録ごとに照会時間を区切る。強制終了した回は次の登録から巡回し、中断した登録も次の周回に含める。同じホスト・同じOS利用者のCodex 0.171.0で、管理されたローカルのapp-serverが元会話を開ける場合に配信する。対象端末が対応していない場合も、配信できなかったことを受付の要対応から確認できる。

反映は `systemctl --user show issue-desk-codex-watch.timer issue-desk-codex-watch.service` と `journalctl --user -u issue-desk-codex-watch.service` で確認する。実機検証の記録にはテスト会話と送信ID、受領、返答終了、元会話の通知ID、原因読取と対処の受付結果、対象PRのマージ確認を同じ対象について時系列で残す。通信障害や停止の条件も、対象端末・稼働版・未配信の受付表示を記録する。

以下は既存のセッション内監視の手順。

- 起動: Monitor（`timeout_ms` 1800000）で `~/.issue-desk/desk follow-issues.ts --desk <共通番号,…> --state <絶対パス>`。`--state` はホームの下の、見張りごとのファイル。張り直しても同じ通知を繰り返さない。共通番号がなく下書きIDだけで終わった相談は `--draft <下書きID,…>` で見張り、`--desk` と併用できる。起票後は共通番号を照合して引き続き見張る。NASの一時キー窓口では `--draft` を指定した見張りは受付交代後に自動再起動されないため、交代で終了したら同じコマンドで起動し直す。
- 通知: 30分ごと（`--interval`、既定1800秒）に読み、変化があったときだけ1行出す。変化が無ければ何も出さない。読み取りの失敗と判断待ちの確かめ直しは60秒後に読み直す。`【要対処】`は進行中の状態の一覧に無いすべての未完了の状態（保留・失敗・回答待ち・未知の状態）、`【停滞】`は進行中のまま60分更新が無いとき、`【読取失敗】`は5回続けて読めないとき、`【完了】`はマージ・クローズ。全件完了で`【見張り終了】`を出して終わる。`【要対処】`・`【停滞】`には題名と、次の担当・次にすること（受付の `nextActor`・`nextAction`）を添える。
- 相談: 質問・起票失敗・エラー・停滞を `【要対処】` で知らせる。起票結果の共通番号や分割子を確認できない場合は追跡を続け、5回続けば `【読取失敗】` で未確認を知らせる。通知は状態ファイルに記録し、確認できるまで重ねない。TODO化と起票せず終了は追跡を終える。404は「相談が見つからない（破棄されたか、この接続では読めない）」と1回知らせて追跡を終える。ほかの読取失敗は追跡を続ける。
- 判断待ち: 残りの全件が利用者の判断待ち（`nextActor` が `user` で進行中の状態でない）と続けて2回読めたら、`【判断待ち】`を1回出して終わる。返事を送ったら同じコマンドで起動し直す。画面で返事をした場合は見張りが止まったままで、受付の要対応（`desk-alerts.ts`）は別に残る。
- 張り直し: Monitorの上限より前（28分）に`【張り直し】`を出して終わる。新しい変化が無い知らせなので、通知の回は同じコマンドで起動し直すだけにし、返答の文を一切書かない（「変化なし」「張り直しました」も書かない）。
- 継続の範囲: 現在のセッションが生きている間だけ。セッションが終わると見張りも止まる。受付の要対応（`desk-alerts.ts`）は別に残る。
- 通知の回: AIは原因を読み、破壊的でなければ自分で対処して報告する。利用者が聞くまで待たない。報告は変わった点・対処・次に誰が何をするかだけを1〜2文で書き、経緯や変わっていない依頼には触れない。

## 返答の作法の検査

チャットのAIの次の失敗を、仕組みで止める。

Stopフックは `desk`・`desk-pc` の `operation` を送信、両窓口の `get` と `desk-get.ts GET` を経路にかかわらず読取として扱う。
Stopフックは `desk-pc` の後ろのスクリプトも `desk` と同じく送信・読取として判定する。例えば 汎用 `operation` は送信、`list-issues.ts` は読取として扱う。

| --- | --- | --- |

| 見張りを付けたのに、状態が変わっても誰にも届かない | Stopフック。setsid・nohup・disown・末尾の `&` で切り離した見張り（watch・monitor・見張り・sleep の待ちループ）を起動した回に、Monitor・run_in_background の Bash・ScheduleWakeup・CronCreate・`scripts/monitor-watch.ts`・`scripts/stage-watch.ts` のどれも無ければ止める。出力ファイルへ書くだけの見張りは通知に数えない | 「5 呼び戻されない見張り」 |

会話記録の新しい種類の行（`attachment`・`mode`・`last-prompt` など）や新しい種類のブロックは読み飛ばし、検査全体を諦めない。Skillの本文などのメタ行は回の区切りにせず、裏の処理の通知は「利用者の発言ではない回」の区切りとして扱う。

`scripts/chat-turn-checks.ts` は互換用の公開入口と窓口・経路の判定を提供し、`chat-shell-parser.ts`・`chat-usage-report.ts` と Stopフックを一緒に配布する。判定は `env` の環境変数代入、`-i`、`-u`、`--unset` に対応する。`sh`・`bash` のスクリプト引数は、配布されるシェルスクリプト `desk`・`desk-pc` の場合に窓口として扱う。その他のスクリプト引数は直接の窓口コマンドや読取コマンドとして扱わない。シェルの `-x` 等の短いオプションと `-o`・`-O` の引数を読み飛ばし、`-c` のコマンド文字列内の各コマンドは検査する。`-i` と `-c` の組合せも検査する。`bash -c 'cat /tmp/result.txt'` も出力の読取として認識する。`-c` を伴わない `-i`、`-s` を含む短縮オプションと `-o`・`-O` を含む結合オプション、未知のオプションや `env -C`、`env -S` は対象外なので使わない。シェル展開や動的に生成されるコマンドは解析しない。

見張り通知の読取と重い前景呼び出しの判定は、`timeout` の秒数と対応するオプションを読み飛ばして中のコマンドを見る。展開は一段だけで、`timeout 30 timeout 10 node scripts/desk-get.ts GET /api/issue?desk=12` のような入れ子は読取と認識せず、重い呼び出しとして安全側に扱う。指定の読取コマンドは重い呼び出しに数えず、その他や解釈できない `timeout` は重いと扱う。Bashツールの `timeout` 値による判定は別に適用する。質問後の選択肢は、記号と区切りの間に `（おすすめ）` を置いてもよい。

### Stop検査の見直しと発動記録

台帳は `server/internal/statistics/stop-checks.json` にある。見直したら結果（残す・直す・外す）と次の見直し日を台帳に書き、PRでレビューする。
発動時は記録ID・検査ID・結果・時刻・プロジェクトだけを `~/.issue-desk/stop-check-fires.jsonl` に追記し、1 MiBを超えると半分以下になるまで古い行から削る。プロジェクトは作業ディレクトリが `~/rc/<名前>` 配下ならその名前、それ以外は `other`。本文・理由・パス・資格情報は記録しない。切り離した `~/.issue-desk/desk stop-check-send.ts` が受付に送り、成功分だけ消す。最大1000件を配列でまとめ、通信障害などで失敗した配列は控えに残す。受付が4xxを返した配列は分割し、単独でも4xxになる行は `~/.issue-desk/stop-check-fires.jsonl.rejected` に隔離する。JSONとして読めない完全な行も同じファイルに隔離し、隔離に失敗した行は控えに残す。隔離後に控えの更新が失敗すると、次回の送信で同じ行が再び隔離されるため、隔離ファイルに重複が生じることがある。隔離ファイルは自動再送しないので、内容と重複を確認して修正し、再送する場合は控えに戻す。発動時に加え、NASとPCの更新タイマー（通常10分ごと）でも再送し、更新処理は最大60秒待つ。タイマーが停止中は再送されない。通信失敗分は次回に再送し、受付は記録IDで重複を除く。控えの追記・縮小・送信後の更新は所有者ごとの `stop-check-fires.jsonl.lock-*` ディレクトリで排他する。同じホストで終了済みと確認できる所有者のロックは自動回収する。別ホストや生存を確認できない所有者のロックは回収しない。ロックを取得できない場合は待機せず、送信後の更新やその回の記録を行わない。

## SSHで別PCに直接PRの実装・検証を分担する

NASで重い実装・検証を始める前に、利用可能な別PCを選び、利用者へ
「【質問分類：新しい権限】対象PC `<PC名>` の `develop` で、この依頼の実装・固定検証を行ってよいですか」
と聞く。対象依頼・PC・操作・必要な期限を質問に含め、A（別PC、おすすめ）とB（NAS）の差を説明する。
NAS以外での実装をプロジェクトが指定している場合、Bを選ぶにはその指定への例外も明示して承認を得る。
直接PRの依頼だけではSSH接続を承認したことにはならない。自動でSSHを許可したり、NASへ戻して重い処理を始めたりしない。

承認後は issue-desk-issue-control Skill の「許可の付与を登録する」に従い、利用者の原文と日時を添え、
`host-ssh` の対象を `<PC名>:develop`、必要最小のTTLで登録する。既存のホスト作業用SSHが発券を判断する。
`develop` は書き込み操作であり、`readOnlyOperations` に入れない。許可の付与はPCと操作に対するものなので、
有効期限中に別の依頼へ流用しない。用が済んだら取り消す。

接続先はLinux PCで、Dockerと稼働Workerが必要。実行スクリプト2件は依頼と一緒に送り、
受付の固定SSHコマンドに埋め込んだSHA-256と一致するものだけを起動する。
個別PCへのスクリプトの事前配置・更新を待たずに使える。
現在稼働中のWorkerと同じDockerイメージと既存Codex認証volumeで専用コンテナを起動する。
コンテナはWorkerと同じcap_dropとsecurity_opt（Codexが内部sandboxを作るための設定）を使い、
ホストのDockerソケットやWorker状態を渡さない。Node 24・Codexログイン・Go等を実装前に確認する。
sandboxを使えない環境では迂回せず失敗を返す。
`tools` で道具を調べ、未配布・未ログイン・sandboxが使えない場合は止める。
新しいAPIキーへの切替やsandboxの迂回をしない。実装はCodexを使用し、実行先の既存モデル設定に従う。

送信元は対象リポジトリの変更のない別cloneを使い、fetch成功と基点SHAを確認する。
作業ツリーの `.tmp/` に依頼文と空の結果フォルダーを用意し、以下の入口を `stage-watch.ts` で包んで実行する。
パスは実際の作業ツリーの絶対パスにする。

```sh
~/.local/bin/node scripts/ssh-development.ts --host <PC名> --cwd <対象clone> --repo mofua-suki/issue-desk-worker --file <依頼文の絶対パス> --out <空の結果フォルダーの絶対パス>
```

依頼はハッシュを検証する実行コード・JSON・Git bundleで送る。資格情報と接続元の未追跡ファイルは送らない。
接続先は毎回専用cloneを作り、AGENTS.mdに従ってCodexをworkspace-write sandboxで動かす。
Workerは `go test ./...`、`go vet ./...`、`gofmt -l .`、Intakeは `sh scripts/verify.sh` を実際に実行する。
AIの自己申告だけでは合格にしない。実装40分、各検証15分を上限とし、実装と検証を合わせて50分で打ち切る。
ホスト側は55分、SSHは約58分の上限を設け、切断時にも専用コンテナを停止・削除する。
利用者への質問にはこれを上限として示し、実測の所要時間と混同しない。

`request-info.json` に実行前の依頼ID・基点・送信内容のハッシュを残す。接続失敗時も消さず、
結果不明のまま同じ作業を新規実行しない。
`result.json` に依頼ID・基点SHA・接続先・各段の終了コード、`change.patch` に新規ファイルを含む差分を回収する。
未取得・対象不一致・検証失敗は成功として扱わない。受信した差分を勝手に適用・pushせず、内容と対象を照合し、
基点に対して適用して独立レビューする。検証済みの木と違う変更を加えたら再検証する。
PR作成・通常マージは既存のmerge-manual-pr Skillとコントローラーに従う。
接続先の専用cloneと一時bundleは終了時に消し、回収した成果物も用が済んだら消す。

実行スクリプトを変えたら `scripts/ssh-development-policy.ts` の `developmentCommand()` で
`host-ssh.json` の `operations.develop` を更新する。不一致は固定テストが止める。

## SSHでリポジトリの固定テストを担当PCで流す

NAS上のClaude remote control・Codexでは、実装がNASでも全体の固定検証・ビルド・race検出はこのSSH入口へ送る。NASでは軽い個別テスト・整形確認だけを行う。issue-desk-intakeは担当表のGT12（`gt12-pro`）を優先し、停止中・利用不可・並行実行で必要なら次順位のNAB-9S（`nab-9s`）へ送る。対象PCへの検証SSHがこの会話で許可済みなら聞き直さず、原文・日時を添えた期限付き許可付与を登録し、用後に取り消す。未許可の接続や恒久の許可付与はしない。SSHで送れない場合は全体検証を保留し、NASへ戻して重い処理を始めない。

NASからissue-desk-intakeの直接PRを検証するときは、確定済みの `chat/` ブランチを `ssh-verify.ts --direct-pr <対象コミットSHA>` で送る。受付では運用代行が有効なNASのPCトークン、登録リポジトリ、担当のGT12、固定操作 `verify` を照合し、対象SHAが受付で読んだ既定枝につながることを確かめ、対象SHAと方針承認を申請記録に残す。発券時にも同じ登録と委任の有効性を確認する。証明書には対象SHAを結び付け、GT12で受け取ったGitオブジェクトからそのコミットを復元し、共通の固定テストを実行する。ほかの検証やSSHには既存の個別承認が適用される。

`host-ssh.json` の `verify` は、リポジトリを問わず、そのリポジトリの固定テストを担当PCで流す汎用の操作。
書き込み・任意コード実行に当たるため `readOnlyOperations` に入れない。接続先は送られたテストの指定（コマンド）を `fleet.json` と照合せず検証しない。
許可の付与の期間中は、そのPCの稼働Workerのイメージの容器の中での任意コード実行を許すことに当たる。許可の付与はPCと操作ごとに利用者の発言で登録し、
対象は `<PC名>:verify`（例 `a9-max:verify`）。1つの許可で、そのPCが担当するどのリポジトリの固定テストも流せる。用が済んだら取り消す。

固定テストのコマンドはWorkerと同じ `fleet.json` の担当PCの設定（`setupCommand`・`testCommand`・`testTimeoutSeconds`）から作り、別に定義しない。

別リポジトリの新しい検証入口へ切り替えるときは、先に対象リポジトリの既定ブランチへ入口をマージし、担当PCで固定検証に成功してから `fleet.json` を更新する。PRのブランチに入口があるだけでは切り替えない。切り替え前に、取得し直した既定ブランチのtreeで入口の存在と対象SHAを確認する。
PC名（`host-ssh.json` の `a9-max` など）は `assignments.json` の `machineName` で担当名（`a9max`）へ対応付ける。
そのPCが担当していないリポジトリは、担当PCの一覧を表示して断る。Macのネイティブ検証（`nativeTestHost`）は対象外。

対象リポジトリの作業ツリー（originが対象リポジトリのclone。末尾の `.git` の有無と owner/name の大文字小文字は問わない）を指定して、NASの配置先の入口を呼ぶ。
申請の根拠（`--evidence`）には、リポジトリ・基点・未コミットの有無・送信本文のSHA-256・`setupCommand`・`testCommand` を書く。
未コミットの変更を含め、削除済みの追跡ファイルと `.tmp/` を除いた tar.gz を送る。送信本文は作業ツリーの `.tmp/` に作り、終わったら消す。

```sh
~/.local/bin/node ~/Workspace/issue-desk-intake/scripts/ssh-host-select.ts --repo mofua-suki/demo-image-generator   # 送り先のPC（許可の付与の対象）
~/.local/bin/node ~/Workspace/issue-desk-intake/scripts/ssh-verify.ts --host auto --repo mofua-suki/demo-image-generator --cwd <作業ツリーの絶対パス> [--reason '<理由>']
```

送り先は、そのリポジトリの実装担当のうち `host-ssh.json` に登録されたPCを担当表（`assignments.json`）の順位の高い順に見て、固定テストを流せる最初のPCにする（`--host auto`、省略時も同じ）。PCを名指しするのは、順位の高いPCが止まっているなど理由があるときだけにする。

接続先では次の順に動く。

1. 実行コード2件（`scripts/ssh-verify-host.sh`・`scripts/ssh-verify-runner.ts`）を標準入力で受け取り、固定SSHコマンドに埋め込んだSHA-256と一致したときだけ動かす。
   個別PCへの事前配置は要らない。
2. 稼働中のWorkerのコンテナ（label `com.docker.compose.service=issue-desk-client`）が1件だけであることを確かめ、その `{{.Image}}` を使う。0件・2件以上なら理由を表示して失敗する。
3. 固定テストの指定と tar.gz を `${TMPDIR:-/tmp}/host-ssh-verify.*` へ受け取る。どちらかが不正なら理由を表示して失敗する。
4. `timeout 5400 docker run --rm --init --cap-drop ALL --security-opt no-new-privileges:true --pull never --network host --user $(id -u):$(id -g) --group-add 1001` で、
   作業場所を `/work`、実行コードを `/runner`（読取専用）に渡す。容器の中では、Workerの固定テストと同じ順に
   `setupCommand` → `package.json` があれば `pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile --config.minimum-release-age=20160` → `testCommand` を流し、最初に失敗した段で止まる。
   `{node}`・`{python}` はそのPCの `fleet.json` の `node`・`python`（Workerのイメージの中の道具）に置き換える。
   setupCommandとpnpmはPCの `testTimeoutSeconds`、testCommandはリポジトリの `testTimeoutSeconds`（無ければPCの値、既定900秒）で各段を打ち切る。
   環境はWorkerの固定テストに合わせる（`HOME=/tmp`・`CI=true`・`TZ=UTC`・`JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=/tmp`・Go/Gradle/pubのキャッシュを `/tmp` 配下など）。資格情報は渡さない。
   issue-desk-intake では、Workerと同じくイメージのCaddy・Chromiumが起動できるときだけ `ISSUE_DESK_TEST_CADDY`・`ISSUE_DESK_TEST_CHROMIUM` を渡す。
   段ごとの上限の合計が5300秒（容器全体の5400秒から100秒の余裕）を超える指定は、入口と接続先の両方で流す前に断る。
   整形（`prettier --write`・`go fmt`）は作業ツリーを書き換えるだけで送信元へ戻らないため流さない。依存の公開後14日制限を回避できる設定がある作業ツリーでは何も流さない。
   例えば demo-image-generator は、Workerと同じくイメージの Python（3.12）で `scripts/setup_test_env.py` が作業ツリーに `.venv` を作り、`.venv/bin/python -m pytest -q` を流す。PC本体の `.venv`・Pythonは使わない。
5. 実行中は1秒ごとに `.` の行を出し、終わったら出力から秘匿の行を除いて末尾64KiBだけ返し、最後に `verify=<終了コード>` を出す。除く行は精算アプリの操作と同じ。
6. 正常終了・失敗・HUP/INT/TERMの中断・接続の切断（PIPE）のどれでも、容器と作業場所を消す。`host-ssh.sh` の打ち切りは5600秒。
   段の時間切れ（124）やシグナル終了（137など）でも、出力の最後の行が同じ `verify=<終了コード>` なら、受付への結果は接続成功・操作の失敗として報告する。

入口の終了コードは `host-ssh.sh` の終了コード（接続先の固定テストの終了コード）。
実行コードを変えたら `scripts/ssh-development-policy.ts` の `verifyCommand()` で `operations.verify` を更新する。不一致は固定テストが止める。
既存の `verify-intake`・`verify-sample-expense-*` は、既存の許可の付与と資料のために残す。

Workerの固定テストとの差は次のとおり。

- `.git` を送らない（作業ツリーのファイルだけ）。Gitの履歴や状態を読むテストはWorkerと結果が変わることがある。
- WorkerはCodexのsandboxの中で、プロキシ経由の通信（JVMにはプロキシ用の `JDK_JAVA_OPTIONS` のagent）で流す。ここは容器の `--network host` で直接通信する。
- 整形（`prettier --write`・`go fmt`）を流さない。Workerの基点の照合・証拠の検査（headの一致など）はしない。

## SSHで精算アプリの固定テストを別PCで流す

`host-ssh.json` の `verify-sample-expense-server`（mofua-suki/sample-expense-server）と
`verify-sample-expense-client`（mofua-suki/sample-expense-client）は、標準入力の tar.gz を接続先のWorkerのイメージで検証する。
どちらも書き込み・任意コード実行に当たるため `readOnlyOperations` に入れない。許可の付与はPCと操作ごとに利用者の発言で登録する。

送る tar.gz は、未コミットの変更を含め、削除済みの追跡ファイルと `.tmp/` は含めない。対象リポジトリの作業ツリーで次のように作り（bash で実行する）、`--input` に渡す。`host-ssh.sh` はNASの配置先のものを絶対パスで呼ぶ。

```bash
mkdir -p .tmp
git ls-files -co --exclude-standard -z | while IFS= read -r -d '' f; do case "$f" in .tmp/*) continue ;; esac; [ -e "$f" ] && printf '%s\0' "$f"; done | tar --null -T - -czf .tmp/verify.tar.gz
~/Workspace/issue-desk-intake/deploy/nas-host/host-ssh.sh --host auto --repo mofua-suki/sample-expense-server --operation verify-sample-expense-server --reason '<理由>' --input .tmp/verify.tar.gz
```

`--host auto --repo <owner/repo>` は、そのリポジトリの実装担当のうち `host-ssh.json` に登録されたPCから担当表の順位が最も高いPCを選び、`送り先: <PC名>` を表示する（`scripts/ssh-host-select.ts`）。許可の付与は、先に `~/.local/bin/node ~/Workspace/issue-desk-intake/scripts/ssh-host-select.ts --repo <owner/repo>` で確かめたPCに登録する。

接続先では次の順に動く。

1. 稼働中のWorkerのコンテナ（label `com.docker.compose.service=issue-desk-client`）が1件だけであることを確かめ、そのコンテナの `{{.Image}}` を使う。0件・2件以上ならタグの新旧では選ばず、理由を表示して失敗する。
2. 標準入力を `mktemp` の作業場所（`${TMPDIR:-/tmp}/host-ssh-verify.*`）へ展開する。展開できなければ理由を表示して失敗する。
3. `timeout 1800 docker run --rm --init --cap-drop ALL --security-opt no-new-privileges:true --pull never --network host --user $(id -u):$(id -g) --group-add 1001` で作業場所だけを `/work` に渡す。`--group-add 1001` は、イメージのFlutter SDKの `bin/cache` が gid 1001 にだけ書き込めるため。
   - server: `HOME=/tmp`・`GRADLE_USER_HOME=/tmp/gradle`・`CI=true` で `gradle --no-daemon test`。
   - client: `PUB_CACHE=/tmp/pub-cache`・`HOME=/tmp`・`FLUTTER_SUPPRESS_ANALYTICS=true`・`CI=true` で
     `flutter pub get && (cd tool/lint && dart pub get) && flutter test && (cd tool/lint && dart analyze && dart test) && dart run tool/mason/verify_templates.dart`。
4. 実行中は1秒ごとに `.` の行を出し、接続が切れていれば書き込みの失敗（PIPE）で気付く。終わったら、docker run の出力から秘匿の行（秘密鍵の範囲と、`token`・`password`・`secret`・`private key`・`idk_`・`idh_` を含む行。大文字小文字を区別しない）を除いてから末尾64KiBだけ返し、最後に `verify=<終了コード>` を出す。
5. 正常終了・失敗・HUP/INT/TERMの中断・接続の切断（PIPE。実行中は、切断後の `.` の書き込みが失敗した時点で気付く）のどれでも、`docker run` を止め、容器と作業場所を消す。後始末なしの強制終了（`KILL`・電源断）では `${TMPDIR:-/tmp}/host-ssh-verify*` と `host-ssh-verify-*` の容器が残る。`host-ssh.sh` の打ち切りは1900秒で、容器内の1800秒より後に切る。


### 非同期の確定・返信の再開と復旧

相談からマージ依頼までの待機手順はskills/issue-desk-operations/SKILL.mdの「受理と完了を分け、同じ識別子で待つ」を使う。CLIが結果を待っていてもPOSTは長い処理の完了を待たず、受付に保存した識別子でGETする。

確定の意図は既存draftsのsubmissionRequest（確定元revision・at・送り手owner/kind）とauto_readyに保存する。受理直後に既存Engineが起票を開始し、Quiesce・Shutdownは結果保存を待つ。起票再開の既存周期は1分。再起動後も同じ下書きから再開する。画面（画像付きも含む）とチャットCLIはasync=trueで返信を送り、同じ送信IDをGETして適用完了を待つ。返信の意図は既存actionsのreply-request:<UUID>に、資格情報を含めず保存する。本文のinput・送り手owner/kind・経路via・status・結果を持ち、queuedは起動時と1分周期で再開する。投稿の重複照合には従来の同じ送信IDのactionsを使う。確定した拒否はfailedとして残す。通信断・5xx等はqueuedとerrorを保存し、同じ送信IDで結果を照合して再開する。自動で別IDの返信を作らない。

新しいDBテーブルや既存レコードの移行は不要。古い版へ戻す前に、下書きのauto_ready/submitting/submit_unknownと、返信GETのqueuedが解消したことを確認する。旧版はreply-requestレコードを実行しないため、queuedを残して戻した場合は対応版へ戻して同じ送信IDで再開する。投稿済みか不明な返信を別IDで送り直さない。既存actionsとdraftsを含む通常のDBバックアップ・復元で意図と二重投稿防止記録を一緒に復元する。

## SSHでWorkerのAIの認証状態を読む

`host-ssh.json` の `ai-auth-status` は、接続先のWorkerの容器（`issue-desk-client`）の中で `claude auth status`・`codex login status` を流し、ログインの有無・方式（`claude.ai`・`長期OAuth`・`APIキー`・`不明`）・契約の種類と、保存済みの資格情報の期限（Claude の `expiresAt`・`refreshTokenExpiresAt`、Codex の `last_refresh`）だけを返す。CLIの文面はそのまま返さず、決まった語（`ChatGPTでログイン`・`APIキーでログイン`・`未ログイン`・`失敗(<終了コード>)`・`状態をJSONで読めません` など）に置き換える。トークン・鍵・メールアドレス・組織IDなど資格情報の値は返さない。容器に入れないときの docker の出力は、`worker-logs` と同じ規則に語頭の `sk-`・`api key` を加えて秘匿の行を除いて8KiBまで返す。最後の行は必ず、ほかの固定操作と同じ `verify=<docker の終了コード>` で、操作の終了コードも同じ値にする（時間切れの124でも、入口は接続成功・操作の失敗として報告する）。
接続先は Docker でWorkerを動かす `gt12-pro`・`a9-max`・`x1-pro1`・`x1-pro2`・`nab-9s` に限る（`operationHosts`）。容器の中でコマンドを流すため `readOnlyOperations` に入れず、許可の付与はPCと操作ごとに利用者の発言で登録する。

```bash
~/Workspace/issue-desk-intake/deploy/nas-host/host-ssh.sh --host gt12-pro --operation ai-auth-status --reason '<理由>'
```

`loggedIn=true` でも、更新用の期限（`refreshExpiresAt`）を過ぎていれば次の呼び出しで認証に失敗する。Codex の `last_refresh` は最後に更新した時刻で、期限そのものではない。
