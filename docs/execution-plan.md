# 受入条件の実行計画

相談の `executionPlan` は版1の正本。条件ごとにID、受入条件の全文、担当、工程、確認方法、期待結果、証拠型、必要能力、入力資料、対象の子を持つ。実装担当は作業ツリー内の変更と固定検証、報告担当は根拠付きの訂正投稿、コントローラーは実機・本番・履歴・別リポジトリ等の外部確認を担う。実装に必要な資料は配信済みのパス・行範囲で示し、資料不足のまま実装へ渡さない。

証拠型は `fixed_test`・`report_comment`・`external_check`。Workerは `fixed_test` の無い計画では実装AIを呼ばない（外部確認だけなら保留、`report_comment` があれば報告だけで終える）ため、分割の無い相談で `changeScope` が `known: true` でファイルを挙げているのに `fixed_test` の受入条件が無ければ、受付は起票前に形式の直しを求める。ファイルを変えない依頼は `changeScope` を `known: false` にする。固定検証の成功を配置・実機確認の成功に使わない。実装AIの自由な完了報告を確認済みの証拠として受け入れない。コントローラーの固定検証はleaseの送信元・世代・計画・SHAと完全な観測を再検証し、報告は対象Issueの実在する投稿・投稿者・目印・本文指紋を照合する。マージの前後でSHAが変わる場合は、受付が保持するPR先頭とマージ済みの対象の対応を使う。

計画、計画指紋、確認証拠は受付が保持し、Workerのviewでは上書きできない。起票時に本文の受入条件と正本を照合し、分割子へ対象条件を選んで継承する。存在しない子、条件のない子、元条件の欠落は拒否する。完了計画・原文・既存の承認証跡も保持する。削除・権限・対象SHAの承認は代替せず、既存ゲートに委ねる項目を別の最終承認として重ねない。

対応するWorkerは `executionPlanVersion: 1` と実測した能力をheartbeatで報告する。計画のある仕事は対応版と必要能力が確認できる実行先へ配る。計画のない既存依頼は従来の経路を使う。能力・入力資料・計画の読取を確認できない場合は、コントローラーが解消する待ちとして表示する。

# 確認と追跡

Issue詳細の `executionProgress` は条件別の担当・方法・期待結果・状態を返す。一覧とsummaryは未完了件数と対象版だけを返す。不正な計画や読めない証拠を0件として扱わない。親相談はマージ済みの子にも未確認条件があれば検証待ちとして追跡する。SHA・世代・計画が変わった確認は再利用しない。

外部確認は既存の許可された経路で実施し、`record-execution-check.ts --desk <共通番号> --file <確認結果.json>` で出典・観測時刻・実測結果を記録する。運用代行を許したPCトークンまたはCLIから受け付け、送信元と送信IDを監査記録へ残す。同じID・同じ内容は一度だけ反映する。報告条件の場合は受付が訂正文を投稿し、その投稿へ確認記録を結び付ける。この操作は実装の再開、使用量上限の追加、利用者の承認を行わない。

固定検証の詳細診断はIssue詳細だけに返す。段階、対象SHAと基点、実行環境、終了理由、プロセス終了状態、秘匿したアサーション周辺を含む。修復AIにも同じ保存済みの診断を渡し、欠測から原因を推定して同じ実装を始めない。

# 保存データの復旧

計画・受領記録は既存のjobs.viewとjob_eventsに保存し、DBの列や既存依頼の本文を移行しない。計画のない既存依頼は従来どおり読み出せる。読めない版や壊れた受領記録は未確認として保持し、空の成功記録に置き換えない。

不具合時は新規計画の生成を止める修正を先に配置し、保存済み計画を処理できる版1対応の受付とWorkerを維持する。保存済み計画がある間に受付だけを未対応版へ戻さない。復旧は既存のDBバックアップ手順で保存領域全体を戻したうえで、同じ対応版を起動する。受領記録だけを削除・書換えたり、世代・対象SHAを付け替えたりしない。同じ送信IDの再照合は保存済みの本文・投稿者・PR・計画を再確認する。API試験では実保存からの再読込と、応答消失後の同一送信、報告保留からの再取得を通している。
