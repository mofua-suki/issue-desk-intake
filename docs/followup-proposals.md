# レビューの後続案（版3）

受付は起動直後と以後1分ごとに、設定されたリポジトリの元Issueを確認する。閉じたIssueも対象に含む。初回はコメントを取得し、その後はGiteaのIssue履歴の `updated_at` またはコメント数が変わったIssueだけ取得する。更新時刻が欠測なら省略せず再取得する。コメントの取得はGiteaの既存のCommentsを使う（配備先はページ指定を無視して全コメントを返す）。版1・版2の自動採用は行わない。

走査位置と未完了候補は既存の `proposal_scans` に保存する。コメント取得失敗時は走査位置を進めず、候補は起票前に保存する。更新のない元Issueのマージ待ち候補は、保存した案からPRの状態だけを再確認する。通常の再起動では未更新Issueのコメントを全件取り直さない。旧head不一致の再判定に対応する前の走査位置は、更新後に一度コメントを再取得する。走査同士だけを排他し、重なった走査は先の走査が終わるまで待つ。待機はキャンセルできる。ネットワーク取得・起票枠待機・起票中は破棄・再投稿と共通のロックを保持しない。採用の判定・保存直前に破棄などを再確認する。

版3の形は `server/internal/proposals/parse.go` と `shared/src/proposal-comment.ts` が正本。受付はJSONだけを読み、表示文から内容を補わない。設定の `intake.proposalWriters`、未指定なら `intake.workerAccounts`、それも未指定なら担当表の `workerAccounts` にある投稿者と、元Issueの参照を照合する。不正・拒否の記録は保持する。旧head不一致によるコメント単位の拒否は、更新後に元Issueのコメントを一度再取得し、保存時と同じ投稿者・内容・指紋と現在のPR判定を照合する。一致した場合は元の拒否理由を保持して再判定済みとし、通常の採用手続きへ進む。不一致と確定した拒否は再判定済みとして保持し、後の走査で解除しない。同じ元Issue・PR・仕事・世代・束の別headが既に採用済みなら、送信結果不明を含めて旧拒否を解除しない。通信失敗は候補を保持して再試行する。内容拒否や破棄は解除しない。

版3の `kind=followup` には `priority` を省略可能で、指定する場合は `{"level":"high","reason":"理由"}` とする。理由は前後の空白を取り除いて1〜500 Unicode文字とし、他のlevel・空の理由・余分な項目は理由付きで拒否する。有効な指定は起票設定と仕事を high にし、理由を下書きの優先度理由に保存する。印と理由は案の指紋に含め、省略した既存の版3は指紋と通常優先度を維持する。版1・2には指定できない。

`pr` は同じリポジトリの設定された公開URLと一致する必要がある。URLを直接取得せず、既存GiteaクライアントでPR番号を照会し、応答の番号・公開URLと `merged=true` を確認する。未マージなら、閉じていても起票しない。マージ前に採用済み下書きは作らず、次の走査で再確認する。恒久的なURL・応答の不一致は拒否記録に保存し、同じエラーを周期ごとに繰り返さない。通信失敗は再確認する。共通番号の欠測は初回に報告して保存し、以後は候補を保持して採番を待つ。

新規採用時、版3のIDが `worker-<job>-<generation>-<hex32>-<batch>` に完全一致する場合は、正規PR応答の `head.sha` も照合する。`hex32` は40桁の16進コミットID文字列そのものをSHA-256にかけた先頭16バイトの小文字16進表記。マージ済みPRの最終headと一致する案を採用する。異なる場合はPRのコミット一覧を空ページまで取得して終端を確認し、PR応答に件数があれば照合する。最終headから第1親をたどった案のhead以降がマージだけで、第2親以降がPRのコミット一覧にない場合に限り、同じ元Issueに許可された投稿者が投稿した、同じPRのより後のheadの案がなければ採用する。PR自身の後続コミットや、より新しい投稿headがあればその候補だけ採用しない。一覧または投稿コメントが取得できない場合や一覧の欠測・不正・未終端では拒否せず再確認する。この判定は親の所属による保守的な判定であり、マージ時の競合解決内容を検査しない。16進部分に大文字を含むIDも形式外として従来の条件で採用する。不一致はそのコメントに限った理由付き拒否として記録する。headの欠測・不正はコメントIDごとに初回に報告して保存し、未完了候補を次回再確認する。旧形式のIssue単位の報告済み状態は候補を特定できないため、更新後に各候補を一度再報告する。通信失敗も再確認する。64桁のSHA-256形式のheadは現在不正として再試行し、その対応は今後の検討事項とする。既に採用済みの下書きの検証・送信結果の照合にはこの条件を適用しない。

投稿者・元Issueなどの照合失敗による拒否は、そのコメントIDだけに適用する（旧記録のscope欠測も同様）。引用返信やコピーの拒否で、正規のWorkerの同じ案を拒否しない。案ID・指紋で別コメントまで除外するのは、明示的な内容拒否（`scope=proposal`）と破棄の記録だけとする。

採用時は決定的なdraftIDと `type=proposal` の案記録をアプリ用PostgreSQLの同じトランザクションで保存する。記録には `draftId`・`fingerprint`・元リポジトリ・元Issue番号・案ID・コメントID・投稿者・案の全項目を保持する。同じIDの内容変更は競合として保持し、既存の下書きを上書きしない。破棄・拒否済みの案、停止・終了した下書き、採用後に下書きが消えた案は自動で復活させない。

起票には既存のfilingサービスと送信意図・照合の仕組みを使う。新しい認証経路は追加しない。案専用の検証器は復旧時と本文生成前後にも、元コメント・投稿者・案の指紋・保存済みの内容・PRのマージを再照合する。採用済み下書きは利用者による優先度変更を受け付けない。印付き案では保存された優先度が high、理由が案と一致しない場合も409で起票を止める。これは採用した案と異なる内容の自動起票を防ぐための照合である。この検証を通過した版3だけを一般の自動起票禁止の例外にし、調査・ほかの自動生成依頼・親の来歴・有事の台帳などの制限は維持する。

本文はマージ済みPR、指摘、期待する動作と直し方、受入条件（テスト方法）の4節。元Issueの共通番号とURLも残す。複数の指摘は同じ番号で対応させ、項目の本文を字下げしたコードブロックにして見出しとして解釈されないようにする。HTMLコメントのマーカーも無害化する。案の実行先を維持し、変更範囲と追加の依存先は既存の起票形式を使う。実装の難易度は起票と同じ規則（README.mdの「実装難易度の自動判定」、`filing.DecideFollowupTier`）で決め、案の変更範囲と指摘ごとのテスト方法があればlight、変更範囲が無ければstandardにする（`disableLightTier` も同じく効く）。モデルはその難易度の実装設定で、判定の元・理由は本文の実行先の行と相談の記録（`implementationTier`）に残す。

範囲の指定がない後続案は元PRの変更ファイルを流用せず、起票された指摘・期待動作・検証方法を含む本文を使って、仕事の作成前に既存の未宣言範囲の見積もりを行う。見積もりが範囲不明を返した場合や失敗した場合、中断後の再開時は既存の未宣言範囲と同じ扱いで全体とする。見積もり機能が利用できない場合は仕事を作らず再試行を待つ。見積もりに成功し、起票者が受付自身で本文を更新できる場合は範囲を本文に補記する。補記できなくても仕事の範囲は保存する。明示された範囲は宣言として維持する。

実装由来の続きのIssueは版1・2のsplit案であり、版3の自動採用対象ではない（`shared/src/proposal-comment.ts`、`server/internal/proposals/adopt.go`）。`server/internal/jobs/transfer_match.go` は報告の `changePaths` がある場合に案の範囲と照合し、下書きは案の `changeScope` を保持する。案の範囲には由来が付かないため、受付側だけでは実装AIの指定とWorkerが補った元の範囲を区別できず、同じ規則への統一には送信側との契約変更が必要となる。版1の範囲なしIssueは `server/internal/filing/issue.go` と `outbox.go` の未宣言見積もりを使う。

採用済み下書きの新規送信時にも同じhead判定を行う。一致しない場合は、下書きを保持し、次の自動再試行を1時間後にする。次回時刻は案記録に保存するため再起動後も有効で、時刻到達後に再照合する。手動送信時もheadを再検証する。

起票後の案記録は `status=notified` と `issue={project,number,url}` を保持する。提出済み下書きがあり案への記録だけ未完了なら、その起票先から復元する。応答不明はdraftIDの起票マーカーで照合し、見つからない間は再POSTしない。

## 保存と復旧

既存の `proposals`・`proposal_scans`・`drafts`・`job_filings` を使用し、新しいテーブル・マイグレーションは追加しない。`proposal_scans` には `type=review_followup_scan` の走査位置・未完了コメント・採番とコメントIDごとのhead欠測や不正の報告済み状態を保存する。旧形式も通常起動で読み込み、候補ごとの状態に移行する。復旧時はPostgreSQLをバックアップ（`runtime/db-backups/`）から戻し、受付の通常起動で保存候補と更新されたIssueを再走査する。記録や下書きを手で消して再送しない。既存の拒否・破棄・競合・停止状態は復旧後も保持される。

## 未採用案の整理（破棄）

`rejected`・`scan_excluded` の案は desk-attention Skillの `GET /api/proposals/dismissal` 手順 で元コメント・内容・指紋を照合し、`POST /api/proposals/dismiss` で理由付きの破棄記録を保存する。元Issue・コメントは削除しない。案IDと指紋が同じ内容だけを除外する。案IDを得られない形式不正の投稿はコメントIDで指定し、元本文のSHA-256を照合してそのコメントだけを整理する。確認結果では保存時の理由と現在の解析結果を分け、旧記録で詳細が保存されていなければその旨を表示する。採用済み・起票中の案との競合は拒否する。指示日時より後に変わった内容にも操作を適用しない。

要対応では、Worker形式の拒否記録について、同じ元Issue・仕事・世代・束の別headの後のコメントが起票済みまたは破棄済みなら表示しない。コメント番号を比較できない場合や採用済み案の記録がある場合は表示を維持する。旧形式のIDは完全一致で判定する。

具体的な引数・指示の条件は [運用スキルの整理手順](../skills/issue-desk-admin/SKILL.md#未採用の後続案を対応不要として整理する) に従う。
