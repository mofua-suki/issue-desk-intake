# 実装の質問・失敗・レビュー保留の内部連携

受付は、停止中の依頼について保存済みの質問・失敗原因・レビュー指摘を読み、既存の回答・再試行の経路を使う。同じ原因に対する送信は1回だけで、送信結果が不明な場合も再送しない。使用量・実装回数・レビュー保留回数の上限、明示された停止、削除・権限の承認待ちは自動で越えない。レビュー回数が未知の場合も未使用とみなさない。

## 修正と再試行

- `retry` は原因を解消済みとする根拠がある場合だけ行う。
- `repair` は、受入条件の範囲内で修正できる未解決の実装失敗・レビュー指摘を実装担当へ返す。原因が解消したとは記録しない。既存の追加指示付き再試行へ接続するため、通常の上限と認可条件は変わらない。
- 修復の根拠は、原因の指紋、参照元、保存済みの原文引用を照合する。修正指示には保存済みの失敗原因またはレビュー全体を付け、検証方法も実装担当へ伝える。指摘を省略しないと上限に収まらない場合は送らない。
- 環境不足、基点由来、比較証拠から原因が確定できない失敗を、実装修正へ送り直さない。本人の判断、破壊的変更、レビューの省略、受入条件や承認の前提変更が必要なら利用者の判断へ戻す。

判断の前に依頼本文・コメント・結果・完了計画などの根拠を固定し、送信前の読み直しで一致を確認する。判断中に変わった場合は、古い根拠の回答・修復を送らず、変わった事実を再照合する。さらに送信前にジョブの世代・状態・原因・利用量・承認待ちを共有DBと照合する。

`repair` は通常の自動復旧だけの内部判断であり、有事の期限切れによる行動には追加しない。起票時の計画や過去の承認記録は、特定の差分・コミットに対する削除・権限承認を代替しない。

## 実行と判断の表示

NASの受付アプリの起動時と1分周期で実行する。更新後1分以上経過した候補を1周期につき最大3件判定する。候補の記録・AIの実行枠・既存Issue操作と同じ寿命で動かし、受付の交代・終了では周期を停止して実行を回収する。外部スケジューラーは使わない。実行経路は `server/internal/startup/job_recovery.go`。

自動復旧の判断には任意の `requiresUser` を保存し、本人判断が必要と明示された通知を判断待ちとして要対応へ表示する。falseと値のない旧記録は監視側へ残し、notifyという名前や理由の文面だけから本人判断と断定しない。回答の検証失敗・修正指示の組立失敗・判断中の前提変更では、JudgeのrequiresUserを保持したままhandoff=trueを保存し、対処不能の原因別引継ぎとして表示する。同じ原因の再発で打ち切った場合、送信結果が不明・拒否された場合は、現在の世代と原因に一致する理由を原因別の引継ぎとして表示する。`causeKey` は対象・原因・世代を識別し、複数行をまとめても元の記録を保持する。古い原因の記録や完了した依頼は表示しない。表示のGETでは再送や確認済みの操作をしない。操作の直前には最新の実装回数・使用量・レビュー保留回数の上限を読み直す。

記録は既存のPostgreSQL JSONへ任意フィールドを追加する。復旧時は原因台帳全体を保持し、再読込後もrequiresUserのtrue・false・欠測とhandoffを保持する。handoffのない旧記録を対処不能と推定しない。旧版へ戻す場合も台帳や履歴を削除しない。旧版は本人判断の有無を区別できないため、要対応の分類を復旧するには対応版へ戻す。

## 公開後の範囲保護と再実装

配布時は、有効なPR・Branch・HeadSHAと公開工程の状態がそろう実行中の仕事を、範囲の重なり判定から除外する。ホストとリポジトリの使用枠には引き続き数える。再試行の世代別マークと追加指示の履歴がある場合は、古いPR情報や `publicationResume` が残っていても範囲を保護する。

再実装後に同じPRを公開し直した場合は、通常のrunning状態報告でPRと公開工程を確認した時点を、既存の `job_events` に `running_publication` として保存する。世代・PR・Branch・HeadSHAを照合し、その後の追加指示で再び保護する。レビュー保留への状態報告も公開完了の履歴として扱う。queuedの公開処理再開とrunningの実装中判定は区別する。

予約元による待機は、そのホストで依存・枠・成果物・継続先・優先待ち・実行中範囲の条件を満たすときだけ行う。配布可能性の照合だけではleaseや `dispatch_offer` を作らない。配布不能な予約元では `scope_reserved` と `release` を新たに記録しない。例外として、優先度1の推定 `*` が実行中範囲との重なりで待つ間、いずれかの担当ホストで重なり以外の条件を満たせば、同じ範囲の低優先度の配布を待たせる。そのホストで公開処理を再開できる依頼は待たせない。待機時間の制限はなく、優先度・状態・範囲が変われば次の配布判定に反映する。実行中の仕事は停止せず、使用枠にも数える。

テーブル変更や移行は不要で、再起動後も状態と履歴を読み直す。旧版へ戻す場合も履歴を削除しない。旧版は追加の公開履歴を使わず従来の範囲保護に戻る。履歴のない既存の公開状態は既存の工程状態と制御履歴で判定し、再実装の完了を確認できなければ保護を維持する。隔離DBの回帰試験で、保存後の再読込、再試行・再公開・追加指示、lease切れ後の再取得を確認する。

## 前提待ちの自動処理

起動時と1分周期に、queued・running・held の後続を持つ closed の先行について自身のPR、または同じリポジトリの other_route の直接PRと merged の merge_manual 依頼結果を照合する。Gitea でマージ済みかつマージコミットを取得できた場合、後続の view の dependencyMerges に先行ID別の repo・pr・mergeCommit・source・checkedAt を保存し、依存の辺を解放する。照合に失敗した辺は待機したまま次の周期に再試行する。

起動時と1分周期に、前提待ちの依頼を記録の有無にかかわらず確認する。未完了の作り手が分かれば依存を接続し、完了済みなら再試行する。自分の前回成果が見えない場合は引き継いで再開し、2回目以降は基点から続ける。作り手を特定できない場合も再試行し、同じ不足の再試行には30分以上の間隔を置く。

同じ不足に対する依存接続と再試行は合計3回まで。通常の実装回数・使用量の上限も適用する。上限、拒否、循環、許可対象外のリポジトリは受付の要対応または `node scripts/desk-alerts.ts` で理由を確認する。
