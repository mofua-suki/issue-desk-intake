# 依頼の分割

## Intake Split Guide (intakeSplit)

受付は起動時に正規化した `assignments.json` の `intakeSplit.lines` と `intakeSplit.files` を参照する。現在は400行・8ファイルで、テストと資料を含む変更見込みがいずれかを**厳密に超え**、分割案がない通常の確定候補に分割案を求める。400行・8ファイルは通り、401行または9ファイルは対象になる。変更範囲に列挙されたパス数や参照資料数は見込みの代用にしない。

保存済み依頼の「## 利用者の判断と根拠」にある「」付き原文が、保存された利用者発言に一致し、同じ発言の日時をUTCに換算した年月日と一致し、引用内で「この依頼は分割しない」のように当該依頼への分割禁止を明示している場合は通過できる。日本時間の日付とは日付変更前後に異なる場合があるため、引用段落にはUTCの日付を記す。照合できない場合や、後の利用者発言で判断を撤回・否定した場合は分割案を求める。AIや代理回答の発言、引用のない指定、別対象の引用、否定、過去事例、規則説明、コードフェンス内の例、heavyReasonだけでは免除しない。

見込みの行数またはファイル数が欠落、不正、負数、整数以外の場合は補完を求める。補完と分割案の再要求は合わせて一度で、相談の追加読取回数とAI使用量の枠に従う。枠がない場合や再回答で解消しない場合は下書きを残して確定しない。再開しても同じ自動要求を繰り返さない。

複数の分割案がある確定候補では、明示された子の行数またはファイル数が同じ閾値を厳密に超え、受入条件が2項目以上ある子を対象にする。利用者の根拠付き分割禁止がなく、上記の共通の継続枠と予算に空きがあれば、対象番号を示して、成果物や同じ検証との結び付きと独立してマージできる挙動を一度見直す。依存・利用者判断・受入条件は保持する。見込みが欠けた子に補完を強制せず、枠や予算がない場合も分割案を通常どおり扱う。

相談詳細 `GET /api/drafts/{id}` の `consultationBudget.contextRead.intakeSize` に `requests`（分割要求回数）、`continuations`、`lines`・`files`、`limits`、`exceeded` が保存される。分割要求時の値は `lastRequest` に保持され、後の見込み更新でも残る。不正・欠落は null。子案の見直し待ちの `notice` は再開時に見直し前の候補を渡すため、一時的に本文を含む。見直し後は消去する。見込みの診断値はAI呼出しの失敗診断とは区別する。代理回答の継続では、代理回答前に保存されていた本文を `intakeSizeProxyEvidence` に保持して引用の出典として使う。旧版へ戻す際は両追加項目を無視でき、既存の相談記録の変換は不要である。バックアップから復旧するときは相談レコード全体を復元し、これらの項目を除外しない。

この検査は従来の riskLines・riskFiles（現在500行・16ファイル）とその例外判定とは別であり、既存のrisk判定を変えない。変更対象4件の目安や入力超過時の自動分割も別の処理である。分割案は起票時に従来の目的・受入条件・依存などの検査を受ける。

## 分けられない理由（heavyReason）の裏付け

分けられない理由（heavyReason）は、上の分割禁止と同じ出典規則で裏付けた場合だけ有効にする。受付は、確定候補の通常起票（`splitIssues` が空）で本文の「## 受入条件」の箇条（コードフェンス内を除く）が2項目以上ある heavyReason と、各分割案のうち `acceptance` が2項目以上ある案の heavyReason を対象に、保存済み本文の「## 利用者の判断と根拠」の引用を `intakeSplit` の検査と同じ照合で確かめる。受入条件が1項目の案は分けられないため対象にしない。

裏付けが無ければ、相談AIに一度だけ続きのターンを渡し、目的・受入条件・依存を保った分割案か、heavyReason を空にした回答を求める。続きのターンを渡せない場合（最後の呼び出し・枠切れ・既に要求済み）や、再回答でも裏付けが無い場合は、対象の heavyReason を空にして回答を通し、返信にその旨を書く。起票は止めない。外した依頼は実装の難易度が通常の判定（`server/internal/filing/tier.go`）になり、本文に `size-exempt:heavy` の目印が付かないため、heavyReason による Workerの量の差し戻しの例外にもならない（他の例外 `hotfix`・`single` の判定は変えない）。依頼者が難易度を指定した依頼は、難易度は指定のままで、外した heavyReason による例外だけが無くなる。止血の依頼（`stallFix`）と「止血」「有事」で始まる heavyReason は対象にしない。照合は `intakeSplit` と同じで、引用内に「この依頼は分割しない」のように当該依頼を指す分割禁止が要る。要求は相談ごとに1回で、後の発言で新しく heavyReason が出た場合は要求せずに外す。

相談詳細の `consultationBudget.contextRead.heavyReason` に `requests`（分割要求の回数）、`continuations`、`locations`（対象。「本文」または「分割案N」）、`cleared`（外した対象）、`pending` を保存する。旧版へ戻す際はこの項目を無視でき、既存の相談記録の変換は不要である。

## 起票時の依存補正

分割の起票は、資料案の不要な依存と、契約案への依存がある実装案どうしの不要な依存を共有規則で外す。依頼者が例外指定した依存、契約案への依存、分類できない範囲、明示した先行Issueと分割外の依存は保持する。起票直前の確認では、保存済み分割計画の依存に加え、子の本文だけにある兄弟依存は「依頼者の指定による依存: 分割案N」の形式に限り採用する。依存番号の妥当性や別プロジェクトの了承の検査も引き続き必要である。

保存済みの子の状態をトランザクション内で確認し、起票結果・送信中・結果不明・試行済み・起票せず終了した子の案は補正しない。補正後の親の `splitIssues` と `splitDependencyCorrections`、未起票の子の本文・依存・`splitBackground` はまとめて保存する。補正履歴には案番号、外した依存、理由区分、補正前後、日時を残し、対象の子の確認済み事項にも理由を記す。送信済みの子の本文や背景は書き換えない。結果不明の送信は保存済みの内容で照合し、自動では再投稿しない。

子の本文には、補正後の依存が現在の案と一致し、外した依存が現在もない履歴だけを記し、同じ依存の注記は一度だけ表示する。保存済みの子が見つからない場合は、起票済みだった可能性を判別できないため再作成せず409で停止する。親と子の保存状態を確認し、必要なら整合するバックアップから復元する。

これらは既存の相談JSONの追加項目であり、バックアップ・復元では親と子のレコード全体を保持する。補正履歴だけを削除して復元せず、計画・子ID・保存済みの送信内容を一緒に復元する。再送は保存済みの親の受付から行い、同じ補正を重ねず、既存の子IDとIssue番号の対応を維持する。
