# 起票前の完了計画と了承記録

新しい相談は、起票前に実装・検証・マージ・配置の担当、必要な環境・前提、完了の確認方法を `completionPlan` に整理する。配置を含まない依頼でも、その理由と完成物を確かめる方法を記録する。分割する場合は全ての子の対象と承認事項を親の計画へ含め、同じ計画を引き継ぐ。

承認事項には対象・操作・条件を記し、実装前に判断できるものを `before_implementation`、差分や対象SHAが確定しないと判断できない最終承認を `after_diff` とする。後者が残ることも起票前の返答で示す。追加承認を予定しない場合の承認一覧は空配列とし、根拠は計画の `basis` に書く。

利用者に示す計画では、`children` を指定した承認の直下に対象の子番号を表示する。省略時は子番号の限定を表示しない。

承認事項の `children` は、対象の分割案の番号を1〜25の重複しない整数配列で指定する。省略・`null`・空配列は全ての子を対象とし、保存時は欄を省略する。不正な値は計画の検査で拒否する。未了の最終承認の判定では、ジョブの `view.splitIndex` が正の整数のときだけ番号を照合し、対象外の子の承認を除く。番号が欠落・不正な場合は承認を減らさない。既に最終承認待ちの保留記録に含まれる承認は、対象外の番号でも記録まで未了のまま保つ。`splitIndex` は受付管理項目であり、Workerの状態報告で追加・変更できない。

承認事項の `gate` は、既存の個別ゲートが差分に応じて求める承認の言い直しだけに指定する。`after_diff` に限り、権限保護は分類 `permission` と gate `permission`、削除承認は分類 `destructive` と gate `deletion` を組み合わせる。それ以外は `null`（保存時は欄を省略）とし、対象SHAへの最終承認や依頼固有のデータ削除・権限ファイル変更などには付けない。`gate` 付き項目は未了の最終承認に数えないが、権限保護・削除承認の個別ゲートは差分を見て従来どおり承認を求める。

利用者の了承を待つのは、分類 `permission`（新しい権限）・`destructive`（破壊的な操作）・`irreversible`（取り返しのつかない操作）の承認事項だけである。分類 `scope`・`basis` の承認事項は計画に記録して報告するが、実装前の了承も実装後の最終承認も待たない。待つ分類の承認事項を1件も持たない計画は、回答を待たずに確定・起票できる。ただし保存済みの計画にあった待つ分類の承認事項を外す・分類を付け替える変更は、利用者の再確認を経る（再確認待ちの間は、承認事項を外しても待機を解かない）。待たない分類の承認事項だけの追加・削除・変更は再確認の理由にしない。以下の了承・再確認・了承の取消しの決まりは、待つ分類の承認事項を持つ計画に適用する。待つ分類の承認事項が無い計画には取り消す了承が無く、後の発言は通常の相談の発言として受付AIが扱う。

実装前の了承が必要な計画は、コントローラーが表示した計画のfingerprintと、その直後の明示回答（`A`・`1-A`・`承認します`・`この計画を承認します`）を照合する。既に同じ対象・操作・条件への肯定指示が保存されている場合は、`approvals[].evidence` の発言ID・発言全文の原文・日時と保存済み発言を照合して引き継ぎ、計画を後から作成したことだけで再確認しない。対象・操作・条件が原文に全て明記されていない引用、別の計画、資料内の承認申告、代理回答、否定・修正の返答は了承にしない。返答には発言ID・原文・日時・保存時の認証種別を記録する。PCトークンや一時キーからの返答はチャットAIによる代理送信の場合があり、認証種別だけで実利用者本人の発言と断定しない。複数の原文を引き継ぐ場合は `completionApproval.evidence` に各発言の出典を持ち、トップレベルのsourceは先頭の代表値にすぎない。後続処理は対象承認ごとの出典を照合する。

この `completionApproval` は計画の提示と返答を照合する監査記録であり、操作の認可ではない。権限ファイル・データ削除・対象SHA・上限超過など、個別操作の承認条件と認証制約は従来どおり適用する。既存の承認手順を通せない操作を、この記録で許可しない。

### 提示計画と書き直し

コントローラーが了承を求めるassistant行には `completionProposal` と、その指紋に一致する構造化済みの `completionPlan` を同時に保存する。履歴へ追加するときに検証・複製するスナップショットであり、後続の候補で書き換えない。AIが返した履歴や了承の自己申告を保存済みの提示記録として取り込まない。回答の照合対象は直前のassistant行で、後からAIが生成した候補ではない。回答と提示の間に別のuser行がある場合は了承にしない。発言ID・原文・RFC3339日時・既存の3認証種別を保存発言と照合する。

事実質問を代理AIが回答する場合も、同時に提示した計画は共通の検証・複製処理を通してassistant行へ保存する。`SaveProxy` がそのassistant行と代理回答を一緒に保存し、Engineが返信の重複追加を省略しても提示記録を失わない。計画の確認質問は利用者に残し、代理回答自体を計画への了承には使わない。

比較は `completion-plan-instruction-v2` で行う。利用者が了承した提示計画の承認事項を指示の基準とする。守るべき認証条件・接続経路などは承認事項の操作または条件へ記載する。basisと工程は承認事項の代わりにならない。

実装前の個別了承、証跡、再確認待ちがなく、利用者が判断する項目が差分後の既存ゲートだけの有効な計画では、承認条件が等価な候補の工程訂正を採用する。承認事項は保存済みの内容を保持し、訂正後の計画を表示と起票にも使う。

承認事項をIDで対応付け、追加・削除、分類・時点、対象（`children` を含む）、操作・条件の変化を再確認する。`children` の省略と空配列は同じものとし、それ以外の配列の変更は再確認する。操作と条件は外側の空白・末尾の句点と「します」「する」を正規化する。対象は外側の空白と末尾の `（案2）` または `(案2)` のような案番号注記だけを除く。その他の括弧や注記、対象内部の文字はそのまま比較し、同一と判定できなければ再確認する。basisと工程の担当・前提・確認方法の差、工程の配列順は再確認の理由にしない。承認事項が空の計画も同様に扱う。

`completionComparison` は適用規則、提示と候補の指紋・構造化計画、変更箇所を記録する。basisと工程の差は記録しても `equivalent` を偽にしない。有効な明示回答が保存済み提示に結び付く場合、`completion-plan-presented-reply-v2` は同じ承認事項の比較を用いて `presentedReplyCompatible` を決め、提示計画とその発言の出典を保持する。候補を了承したものとはせず、個別操作の認可も代替しない。形式が不正な計画は判定不能として再確認する。

了承待ちのAIには保存した提示計画をそのまま返すよう固定指示する。完全一致しない「A（補足）」「A: …」「1-A、2-A」等は新たな了承にせず、返答で `A / 1-A / 承認します / この計画を承認します` の4形式を案内する。その返答を了承済みの保存発言として表示しない。外側の空白は従来どおり除いて照合する。

新しいuser発言による対象・条件・判断の前提の変更は、候補の自由文の書き直しとして処理しない。取消し・条件変更を含む発言は古い了承を無効にする。それ以外の追加回答だけで了承を取り消さない。「計画は変更しません」「計画を変えずに」のように計画を据え置くと述べる発言は取消しに数えない。ただし「変更しませんが…」のように別の指示が続く発言は取消しのままにする。新しい発言の後も承認事項の対象・操作・条件を比較し、取消しや条件変更を含む発言は以前の了承を無効にする。自由文の意味から新しい指示や了承を推定しない。別の承認事項に対する保存済みの肯定指示を引き継ぐ場合は、計画内のevidenceにある発言ID・原文・日時を照合し、各引用の出典と対象・操作・条件を個別に検証する。この複数引用の経路を新しいA回答や候補自由文の了承には使わない。

承認事項の保護項目に差がある場合、またはその同一性を判定できない場合は、そのフィールドを質問に示して新しい計画を提示する。`completionReconfirmation` に対象指紋、`completionReconfirmationAfter` に再確認開始時の保存発言件数を保存する。説明要求・古い引用・承認一覧の削除では解除しない。以前の計画へ戻しても過去のAを使い回さず、開始後に新しく提示した計画への明示回答が必要になる。再回答後の候補は有効な明示回答の専用規則で判定し、提示計画を保持する。取消し・条件付き回答は了承にしない。起票時にも再確認の対象・開始時点・発言と了承記録を照合し、承認事項が空になった計画でも待機を迂回できない。分割起票も親を先に再検証し、子へ対象指紋・開始時点・提示履歴・了承を引き継ぐ。分割の保存指紋にも待機状態を含め、部分的な再試行で脱落させない。

相談を分割すると、各子は子固有の依頼文に続けて親の発言履歴を保持し、計画・了承・提示・再確認待ちを引き継ぐ。再確認開始位置は子固有の依頼文を含む履歴の位置に合わせる。子の起票時にも保存発言と待機状態を再検証する。

分割子を保存した後、POST前の検証や本文作成に失敗し、親で計画を変更して新しく了承した場合、再試行で更新可能な子には計画・了承・再確認状態と `messages` を同じトランザクションで更新する。開始時点は引き継いだ履歴に対する位置であり、古い子の履歴と新しい了承を組み合わせない。承認事項が空の計画も同様に扱う。更新は従来の未送信条件を満たす子に限り、送信済み・送信結果が不明・ジョブを準備済みの子の計画を上書きしない。

### 既存記録と復旧

比較監査の `presentedPlan` と `presentedReplyCompatible` を含め、保存形式は既存のPostgreSQL JSONへフィールドを追加する方式で、履歴の一括変換は行わない。構造化スナップショットのない旧履歴は、保存済みの有効計画が提示指紋と完全一致するときだけ対象を復元して使う。今回のAI候補から欠けた提示計画を補完しない。保存スナップショットが不正または指紋不一致の場合は、旧形式へ戻らず再確認する。本人発言を推測で補完しない。開始時点のない旧再確認待ちは、最新のuser行がその提示計画への明示回答である場合だけ解除できる。

復旧はREADMEの既存PostgreSQLの保持・切戻し条件に従い、計画・提示履歴・応答・了承・再確認待ちのJSONを一緒に保持する。保存済み計画が不正な場合、有効な提示と回答を照合できなければ候補を初回計画として扱わず再確認する。欠けた履歴や応答を手作業で捏造して補わず、確認不能なら再提示して回答を得る。旧版へ戻す場合は新しい再確認開始時点を検証できないため、再確認待ちの下書きを旧版で起票せず、新版へ復旧して確認を完了する。

ジョブの実装後の承認記録 `view.finalApprovals` は、承認ID・対象head SHA・発言ID・原文・日時・送信経路・送信元PCと承認事項の指紋を保持する。未了の最終承認に数えるのは、待つ分類の `after_diff` の承認事項だけである（範囲の拡大だけでは最終承認を求めない）。ただし、既に最終承認待ちで保留されているジョブ（`view.finalApprovalHold` が今の世代・head と一致）は、保留の記録（`approvals`）にある `scope`・`basis`・範囲拡大の承認事項も未了のまま保つ。保留の記録に無い待たない分類の項目は、保留中も数えない。この保留を解くのは最終承認の記録だけだからである。承認事項の対象・操作・条件などが変わると指紋が変わり、以前の記録は使えない。承認の新規受付は現在のhead SHAとの一致を必須とする。

状態報告の `diffFingerprint` は、API仕様の三点差分の指紋をジョブ・PR・branch・実装世代・head SHAに結び付けて受付が保存する。承認時にその対象と一致する有効な指紋を承認記録へ複製し、承認リクエストから差分指紋を指定することはできない。承認ID・承認事項の指紋が一致し、同じhead SHAか、同じジョブ・PR・branchの差分指紋が一致し、現在の実装世代が承認時以上の場合に承認を有効とする。指紋がない旧承認はSHA一致で判定し、後から指紋を補完しない。指紋の欠落・消去・不正・対象不整合では異なるheadへ引き継がない。削除・権限保護など個別SHAへの承認経路や、公開済み成果物と再開条件の検査は引き続き適用する。

同一差分による引継ぎは状態報告の保存トランザクションで `view.finalApprovalTransfers` へ記録する。各記録は承認ID（`id`）、承認事項の指紋（`fingerprint`）、原承認の発言ID（`messageId`）、原承認のSHA（`fromHead`）、新head（`toHead`）、差分指紋（`diffFingerprint`）、元と先の実装世代（`fromGeneration`・`toGeneration`）、日時（`at`）を保持する。原承認のSHA・発言・日時・送信経路・PCは書き換えない。異なるheadでの承認判定では、現在の指紋と対象に加えて、これらの項目が原承認と現在headに一致し、有効な日時を持つ履歴を照合する。旧形式の世代欄がない履歴は同世代の場合だけ有効とする。履歴が欠落・不整合なら未了とし、読取で補完しない。再報告・再取得で同じ引継ぎを重複させず、未了承認の読取では履歴を変更しない。指紋・承認記録・引継ぎ履歴は受付の管理項目であり、Workerのview・lease progressからは上書きできない。

保存形式は既存JSONへの項目追加で、旧データの一括変換は行わない。復旧時はジョブのview（指紋の対象・原承認・引継ぎ履歴を含む）・PR・branch・実装世代・head SHA・範囲を一緒に保持し、再読込後に未了承認を確認する。この承認判定に対応しない旧版へ戻すときは自動マージを停止し、対応版を復旧して未了承認を再確認してから再開する。欠けた発言や承認記録は捏造せず、改めて利用者の判断を得る。

既存の相談は計画を後付けしない限り従来どおり扱い、新しい相談では計画が欠落・不正なら起票前に受付AIが一度修復する。形式の修復を利用者への技術質問に置き換えない。

受付AIの承認項目は `children` を必須欄とし、対象の分割案番号（1始まり）の整数配列、全ての子が対象・対象不明・非分割の場合は `null` を返す。`null` は保存時には欄省略と同じ指紋になる。起票前に分割件数を超える対象番号や非分割への対象番号指定を409で拒否し、子の保存・Issue作成に進まない。

起票時には計画と了承記録をジョブのviewへ保存し、Issue本文に計画を記す。子は親と同じ計画を保持し、下書きの `splitIndex` をジョブのviewへ記録する。最終起票本文のSHA-256を `completionPlanEvidence.bodySHA256` に記録し、後続処理で現在の本文と照合できるようにする。本文・前提が一致しない記録を、実装質問への回答や再試行の許可根拠へ流用しない。

保存した計画確認質問を解消したターンは、その質問と確定を断定する文を除き、AIの説明と後続の保留通知を保持する。了承の誤表示や候補への付け替えを訂正する必要がある場合は定型文に置換する。了承待ち・了承後の説明本文と、後続の新規リポジトリ・複数プロジェクトの案内は保持する。専用規則で再確認するときは、原因となる保護項目の差と、監査記録のみの自由文差を質問文で分ける。

提示計画への有効な明示回答が比較により確定した場合、保存されたコントローラーの計画確認質問が再出力されても解消する。

計画の了承を求める質問はコントローラーが出す1つに統一し、受付AIには固定指示で了承質問を自分で追加させない。それでも受付AIが計画の了承質問（`A / 1-A / 承認します / この計画を承認します` の4形式を案内し、「2-A」「2.」など別の番号付きの判断を含まない質問）を返した場合、コントローラーがそのターンで了承を記録し、起票時と同じ出典検証（`completionplan.Check`）を通したときに限り、その質問と理由を取り除く。了承を確定できない場合はその質問を取り除いてコントローラーの計画確認質問1つだけを残す。受付AIの質問・理由・了承の自己申告は了承の証拠にしない。これに当たらないAIの質問や他の確認は残し、残存質問があれば起票案を確定しない。

了承の確定後に、提示記録（`completionProposal`・`completionPlan`）を持たないassistant行への完全一致の記号回答（「A」「1-A」など）があっても、それを新しい了承にも取消しにも数えない。照合はそれより前の、提示記録を持つ行への回答へ進み、その元の提示と発言出典を検証した `completionApproval` を保持する。起票時の `Check`・`CheckPresented` も同じ履歴を同じように扱う。再確認開始位置より前の回答、提示記録の一部だけを持つ行、取消し・条件変更を含む回答、別のuser行を挟んだ回答は従来どおり了承にしない。後の記号回答があっても、候補の承認事項を提示計画と比較する。質問解消後も資料・既存依頼・計画の検査と保留条件を通して起票可否を判断する。計画の了承は個別操作の認可を代替しない。
