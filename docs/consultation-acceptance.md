# 受付の受入条件

ready=trueの回答では、本文の「## 受入条件」節の各箇条書き（番号付きも含む）と、各分割案のacceptanceの全項目に「確認: <確認手段> → 期待: <期待結果>」を書く。確認手段はコマンド、テスト名、APIのメソッドとパス、または「画面: <画面名と操作>」を名指しする。期待結果には出力、終了コード、件数、表示、状態や測定値の合格条件を書く。単独のコマンドはバッククォートで囲むと判別しやすくなります。liveCheckの観察可能な数値と合格値も使える。空欄や「検証する」だけでは不足する。

本文では節外、箇条書きでない行、バッククォートやチルダのコードフェンス内、マージ後の運用作業節を検査しない。未閉鎖フェンスは本文末尾まで続く。継続行は同じ項目に含め、別の項目では補わない。節がない場合は既存の検査に委ねる。

欠落があれば既存の修復枠内で1回補完を試みる。補完できない場合や枠がない場合はready=falseとし、対象と不足を理由に残す。記載されたコマンドやAPIは検査時に実行しない。

期待結果の機械検査は空欄や既知の曖昧な表現などを検出するもので、意味や具体性を完全には判定できない。特定の語彙に一致することは要求しないため、内容が確認可能な合格条件になっているかは受付時に判断する。
