# 変更で不要になったファイル・テストを消す

機能の削除・置き換え・改名・移動を実装するときは、その変更で不要になったものを同じ変更の中で消す。後始末だけを別の依頼へ残さない。

## 対象

- その変更で使われなくなったファイル。コード・スクリプト・設定・資料・テスト用の部品を含む。
- 守る対象が無くなったテストと、他と完全に重複したテスト。重複は、検証する振る舞い・条件・アサーションまで確認し、固有の回帰検証を失わない場合に限る。

ルートに temporary.json があるリポジトリだけ、一度きりの確認で守る対象が無くなるテストを一時テストとして専用ファイルに置き、temporary.json に登録する。無いリポジトリでは登録簿を作らない。今後の再導入を止める価値がある恒久テストは登録しない。

## 消す前の確認

参照が無いことを、推測ではなく事実で確かめる。

1. git grep などで、ファイル名・モジュール名・export 名をリポジトリ全体から検索する。Gitが使えない環境では rg などでファイルを直接検索する。
2. `package.json` の scripts、CI、Dockerfile、compose、deploy、資料からの参照を確認する。import の検索だけで判断しない。
3. 文字列で組み立てる動的な読み込みを確認する。名前の一部・ディレクトリの列挙・設定からの読み込みも調べる。
4. 消した後に、残る参照と関連テストを確認し、変更の本来の振る舞いと残す回帰検証が保たれていることを確かめる。

## 消さないもの

外から使われている可能性を否定できないものは消さない。各プロジェクトの `AGENTS.md` が残すと決めているものも残す。たとえば issue-desk は、切り出し元のファイルを削除せず、再エクスポートで既存の import を保つと決めている。このような互換性の入口は不要とは扱わない。

消さなかったものは、対象と残した理由、確認できた範囲を報告する。

## 対象外とテストの保護

その変更が不要にしたものだけを扱い、既存の未変更部分は棚卸ししない。1回きりの整理とは別の決まりである。

失敗を通すためのテストの削除・skip・弱体化は、この決まりの対象ではない。各プロジェクトの禁止はそのまま有効である。たとえば demo-image-culling の AGENTS.md にある禁止文「テストを削除・スキップ・弱体化して通さない」に従う。テストが失敗したことは、守る対象が無くなった根拠にはならない。

## issue-desk の監視で公開する場合

issue-desk の監視で公開するリポジトリでは、テストファイルを丸ごと消してテスト宣言の件数が減る場合も、コントローラーはレビュー前に保留せず、削除したテストの一覧と件数を判断材料に独立レビューへ進め、独立レビューが妥当性を判断する。移動先が無い・差分を読めない場合も同じである。消えるテストが守っていた挙動が本体と一緒に無くなるか、ほかのテストで守られているか、残すべき挙動のテストが消えていないかを確かめる。承認・指摘なし・不確実性なし・破壊的変更なしなら利用者の承認なしでマージし、疑いがあれば保留・差し戻しになる。

それでも消すべきものは同じ変更で消し、参照確認の根拠、守る対象が無くなった理由または完全に重複した根拠、公開時の判断材料を報告する。件数を保つための無意味なテストや、確認を避けるための skip を足さない。公開の判定はコントローラーに任せる。
