# issue-deskの受付経由のIssue操作

操作スクリプト・API・チャット配布の正本は `mofua-suki/issue-desk-intake`。窓口は `docs/chat-operations.md`、APIは `api/openapi/`、各操作の引数はこのSkillのrefsと該当スクリプトの使い方を照合する。Workerの実装・hostd・局所更新の正本は `mofua-suki/issue-desk-worker`。既存のIssueのprojectは元のまま扱い、リポジトリ名が変わったという理由だけで別projectへ送り直さない。

要対応等は [issue-desk-admin](../issue-desk-admin/SKILL.md) を参照する。

既存Issueの操作・許可の付与は [issue-desk-issue-control](../issue-desk-issue-control/SKILL.md)、直接PRの作成・マージは [merge-manual-pr](../merge-manual-pr/SKILL.md) を参照する。

## 共通の決まり

- 利用者から起票・TODO保存・再試行・クローズの依頼を受けたら、エージェント自身がこのSkillのスクリプトで実施する。利用者にGiteaでの起票・受付画面での入力やボタン操作を求めない。利用者に頼むのは、受付が止まっているとき、運用の代行を許したトークンが無いPCで再試行・返信が要るとき（受付画面の「再試行する」・Issue画面）、自分で確かめられないクローズ依頼の確認待ち（受付の要対応）など、各節が利用者の判断・操作を求める場合だけ。
- 受付画面のボタン・入力欄はどれも受付のAPIの呼び出しなので、「画面でしかできない」と言う前に `api/openapi/` の経路を確かめる（利用者だけに許した操作は除く）。
- 止まった・失敗した Issue は原因を調べて自分で直し、最後まで通す（チャットの変更は chat-instructions.md の直接PRの明示条件に従い、通常は受付へ修正依頼）。途中の進捗の報告はしない（完了か利用者の判断時だけ報告）。目的は利用枠あたりの Issue の処理件数。無駄を削りペースは落とさない。
- Issueの作成・読み取り・終了・再試行とTODOの保存は、下のスクリプトで受付サービスを通す。GiteaのIssue API・Web画面・`/codex retry` の手書きコメントで直接操作しない。受付が止まっていて使えないときは、別の方法で回り込まず利用者に伝える。
- 依頼文を書く前に `~/.issue-desk/desk create-issue.ts --spec` の「依頼1件の大きさ」を読む。変更対象は1件につき4ファイルが目安で、超えると送信時に警告して相談を続ける。分割禁止を利用者の判断として記す場合は、その判断を支持する発言の原文を「」で引用し、発言日時を添える。資料を圧縮しても入力上限を超えたときの自動分割は、利用者発言に含まれる文字列「分割しない」で停止するため、出典規則と結果が異なる場合がある。件数の数え方と自動分割の制約も同じ節で確認する。
- 対象は `--project <owner/repo>` で指定する（受付に登録されたプロジェクトだけ）。作業中のリポジトリがissue-desk以外でも同じスクリプトを使う。
- `--number` はGiteaのIssue番号。利用者への報告は受付の共通番号（`desk`）で行う。
- 一時キーは受付と同じPC上だけの方式（A9 MAXへ受付を戻した場合だけ）。Issue制御の「一時キー」「直接閉じる」はその場合の説明。
- NAS の Skillと常設指示は NAS の更新（deploy/nas/update-skills.sh）が配る。

呼び出す前に、同じSkillに同梱した [共通の接続と登録の詳細](refs/connection.md) を必ず読む。窓口 `~/.issue-desk/desk` の呼び出しとホーム内のファイル・トークン接続と許可範囲・監視の開始条件は、この補足ファイルを共通の決まりの一部とする。

スクリプトのない受付APIを直接呼ぶ手順は [issue-desk-api](../issue-desk-api/SKILL.md) を参照する。

## 送信前のIssue番号確認

起票、相談への回答（`create-issue.ts --draft`）、Issueへの返信、TODO保存、保存済みTODOの本文更新（汎用 operation のTODO保存手順）の送信前に、本文中のIssue参照を次の順序で確認する。`runner.log`・`desk-alerts`・Giteaのコメントなど、Gitea番号しか出ない資料から拾った参照にも同じ手順を適用する。

1. **参照元で対象を特定する**: 資料のリポジトリ名・URL・前後の記録から対象のリポジトリ（`owner/repo`）とGitea番号を特定する。作業中のリポジトリと同じとは限らない。PR番号やコマンド引数を本文のIssue参照と混同しない。
2. **受付の結果で照合する**: [issue-desk-issue-control](../issue-desk-issue-control/SKILL.md) の「読む・一覧/検索する」の汎用GET手順を使い、結果のリポジトリ・Gitea番号・題名や内容が参照元の対象Issueと一致することを確かめ、そのIssueの `desk` を照合する。一覧は `hasMore` が false になるまで同じ条件でqueryの `page` を増やして確認する。途中の読取失敗や `hasMore` の欠落は全件確認済みにしない。一覧で対象が見つからなければ詳細を取得し、不在だけで共通番号なしと判断しない。取得失敗や対象不明を共通番号なしと断定せず、番号の対応を推測しない。照合できない参照は送信せず、読取の再試行や参照元の確認で解消し、解消できなければ理由を利用者に伝える。
3. **本文を書き直す**: 共通番号が確認できた参照は「共通番号N（owner/repo#Gitea番号）」へ書き直す（形の例: 共通番号1463（mofua-suki/issue-desk-intake#49）。番号は説明用で、実在の記録ではない）。対象Issueは確認できたが共通番号が無い・未確定の場合は「owner/repo#Gitea番号」と書く。裸の「#Gitea番号」で代用しない。
4. **送信前に再点検する**: 実際に送る本文（`--text`・`--file`・標準入力）全体のIssue参照を再点検し、引用・ログから転記した箇所も含め、照合した表記へそろえたことを確かめてから送る。スクリプトの `--number` は引き続きGitea番号で、共通番号へ変換しない。利用者への報告にも同じ表記を使う。

## 受理と完了を分け、同じ識別子で待つ

相談開始からマージ依頼まで、長い処理は受付へ保存して識別子を受け取り、依頼した側が結果を待つ。HTTP成功・CLI終了コード0・待機期限の到達だけで完了としない。CLI自身がGETを繰り返す場合も、受付のPOSTは処理の終了まで接続を保持しない。

| 段 | 受付の応答・識別子 | 相談側の待機と完了条件 |
| --- | --- | --- |
| 相談開始 | POST /api/issues の202、accepted=true、id・requestId・receiptIdを保存 | create-issue.tsが同じ下書きIDでGET。中断後は --check <ID>。質問待ちなら同じ相談で回答し、submittedかつissue/issuesの実在を確認して起票完了。 |
| 相談への回答・再試行 | POST /api/drafts/<ID>/chat の202、同じ下書きID。通常回答のid/messageIdも保存 | create-issue.tsが同IDでGET。thinking・auto_ready・submittingは待機中。回答送信の --draft と読取専用の --check を混同しない。 |
| 確定して起票 | POST /api/drafts/<ID>/submit の202、accepted=true、id=下書きID。確定元revisionも保存 | --submitがGETで結果を待つ。再開は --check <ID>。auto_readyは受付済みの起票待ちで、受理直後にEngineが起票し、1分周期・再起動時の起票再開でも回収する。submittedかつissue/issuesが完了。 |
| 実装AIへの返信 | reply-issue.tsがPOST /api/commentへasync=trueを送り、202、accepted=true、送信IDを保存 | GET /api/comment?id=<送信ID>でdoneかつresultを確認。queuedは未完了、failedは理由を読む。その後の実装・レビュー・マージは共通番号のfollow-issues.tsで追う。詳細はissue-desk-issue-control。 |
| PR作成・マージ依頼 | POST /api/v1/requestsの201（同一送信の照合は200）、request.idを保存 | merge-manual-prの手順で同IDをGET。doneかつresult.status=created/mergedを照合するまで待つ。 |

受理の応答を失った場合は、保存した接続先・送り手・対象・送信IDで照合する。識別子が表示済みなら読取を続け、新しい相談や別IDを作らない。読取失敗・失敗状態・欠測・未知の状態は成功にしない。相談CLIの待機期限後も受付の処理は続くため、同じIDの --check を続ける。起票または修正指示後は、このSkillとchat-operations.mdの起票後の見張りも行う。


## 起票する

<!-- issue-desk:tier-policy:begin -->
正本: `server/internal/tierpolicy/policy.go`。`cd server && go run ./cmd/generate-tier-policy --root ..` で生成する。

新しい相談の難易度は依頼元のAIが内容から選び、--tier（TODOの/startではtier）を必ず指定して根拠を本文へ残す。受付は始めの難易度判定をせず、未指定はTIER_REQUIREDで断る。相談の段と根拠はAIが内容から選び、通常の選択を利用者へ質問しない。AIの見積もりや選択を利用者の明示指定として引用・保存しない。利用者の実際の指定がある場合は原文と日時を残し、その指定と既存の固定規則を維持する。モデル名と段の対応は現在の設定を使う。途中の難易度変更は既存のraiseTier/escalateと固定・承認の条件に従い、指定の上書きや新しい承認経路を作らない。今の段で分析が難しい場合だけ具体的理由を添えて引き上げを申告し、質問で解決する場合や高・固定値では申告しない。

相談と実装の判定基準・引継ぎは [難易度と分割](refs/tier-and-splitting.md)、確定前は [相談の確定](../issue-desk-finalization/SKILL.md) を読む。
<!-- issue-desk:tier-policy:end -->

調査Issue・自動起票は禁止。

例外として、受付は信頼されたWorkerの版3レビュー後続案だけを、PRのマージ・元コメント・保存済みの内容を再検証して自動起票する。チャットのAIが任意の依頼を自動起票する許可ではない。条件と保存・整理の方法は [レビューの後続案](../../docs/followup-proposals.md) を参照する。

[相談元](refs/agent-policy.md)

- 利用者の判断による起票は「## 利用者の判断と根拠」に判断ごとの利用者の発言を引用し根拠の事実一覧（各事実の確認済み／推定と根拠）を書く。`chat-instructions.md` の(a)(b)参照。
- `DECISION_BASIS_MISMATCH` は recovery に従う。`correct_requester_facts` は同じ相談へ事実訂正を返信。ほかも利用者の再判断を待たず、訂正した事実を踏まえた進め方を同じ相談へ返信し、判断の記録で報告する（進め方が聞いてよい分類に当たるときだけ聞く）。新しい依頼として再送しない。

送信前に、次の順で依頼と計画を照合する。

1. 新しい依頼を送る前に、見込みの変更ファイル数を数える。4件を大きく超え、単独でマージできる挙動が2つ以上あるなら、送る前に分ける。
2. `--draft` で計画の了承を送る前に、受付の見込み（`estimate.files`・`estimate.lines`）と依頼文のファイル数・行数の見込みを比べる。受付の見込み（estimate.files・estimate.lines）が依頼文の見込みより広がっていたら、計画の了承を送らず、相談を終えて分けて起票する。相談の終了には issue-desk-admin Skillの終了APIを使う。見込みを読めない場合は未確認として扱う。
3. `--draft` で前提・方針を追加する前に、保存済みの提示計画（`completionPlan`）を読み、内容が食い違わないか照合する。食い違う場合は、計画を直す回答として送る。

1. 送信前に、新しい依頼と相談への回答（`create-issue.ts --draft`）の本文について、上の「送信前のIssue番号確認」の手順を行う。
2. 照合して書き直した本文を、点検警告の確認・修正後に送る。

```
~/.issue-desk/desk create-issue.ts --project <owner/repo> --tier light|standard|heavy --provider codex|claude --consultation-provider codex|claude --file <依頼.md>
~/.issue-desk/desk create-issue.ts --draft <下書きID> --text "<受付AIの質問への回答>"
~/.issue-desk/desk create-issue.ts --draft <下書きID> --submit
~/.issue-desk/desk create-issue.ts --check <下書きID>
```

- `--provider` は実装の実行先。利用者がClaudeを指示したときだけ `claude` にし、指示が無ければ `codex` を指定する（利用者に確認しない。省略時もcodex。新しい依頼にだけ付け、`--draft` とは同時に付けない）。
- `--priority high|normal` は利用者が明示したときに付ける（`high` は「割り込み」: 実行中の作業を中断せず、AIの判定や通常依頼／フォローアップの区分より先に着手する。以前の「優先」と同じ値。新しい依頼にだけ。省略すると自動）。
- `high` は、エージェントの判断による割り込みの条件（パイプラインを止めている・止めかけている問題の修正、利用枠・時間の大きな無駄を止める対策、利用者が急ぎと言ったもの、先に入らないと後続の依頼が進まない土台）に当てはまると判断したときも自分で付けてよい。普通の機能追加・フォローアップ・資料の整理には付けない。
- `high` には `--priority-reason "<理由>"`（1〜500文字）を必ず添える。受付が記録して画面に出す。同じプロジェクトで待っている割り込みの件数では断られない。
- `--tier light|standard|heavy` は相談の難易度（低・中・高）。新しい依頼（`--project`）には必ず付ける。依頼元のAIが上の共通基準で依頼の難しさを判断して選び、[難易度と分割](refs/tier-and-splitting.md)に従う。受付は難易度を判定しないので、無いと create-issue.ts が送らずに止まり、受付も400（`TIER_REQUIRED`）で断る。実装モデルは不変。
- `--tier` は `--draft` と一緒にも使える（任意）。相談の途中で難易度を変えるときは回答に `--draft <下書きID> --tier light|standard|heavy` を付ける（次のターンから変わり、記録は source=user と history に残る。現在と同じ難易度は変更にならず、fixed の相談では変えない）。途中の変更は利用者が明示したときだけ付け、AIが自分の判断で付け替えない。
- `--hold` は相談だけで始め、受付AIが起票できると判断しても自動では起票しない（新しい依頼にだけ）。方針が固まったら `--draft <下書きID> --submit` で確定して起票する（確定時に重複・依存・範囲の確認が走る。`--submit` は本文・`--tier`・`--hold` と同時に付けない）。トークン接続では自分の `--hold` の下書きだけ確定できる。
- `--implementation-tier light|standard|heavy` は利用者が実装の難易度（light: 低、standard: 中、heavy: 高）を明示したときだけ付ける（実装のモデル・推論レベルを管理設定のその難易度にする。新しい依頼にだけ。省略すると受付が起票時に判定する。実行先は変わらない）。AIの判断で付けない。
- 受付AIが質問を返したら、答えられるものは `--draft` で答え、利用者の判断が要るものだけ利用者に聞く。起票は受付AIが行い、自動で開始する。
- 新規相談のPOSTの応答を失ったら、表示された送信IDを `--send-id <ID>` に付け、同じ接続先・送り手・本文・引数で再実行する。標準入力や `--file` も同じ本文を渡す。`下書き: <ID>` が表示されていれば送り直さず `--check <下書きID>` で確認する。`--check` は読むだけで、`--draft` は回答を送るので確認には使わない。終了コード0でも処理中なら未完了。0 が状態を受け取れた、1 が受付へ送れなかった・受付AIのエラー、2 が受付済みで結果が未確認。
- 新規相談以外の送信（`--draft` の回答送信など）で接続エラーが起きたら、送り直す前に `--check <下書きID>` や受付の依頼一覧で届いていないかを確かめる。
- **起票前に重複を確かめる**: `list-issues.ts --duplicates --project <owner/repo> --query <題名の語>` で依頼・相談・TODOを照合し、各種別の候補と読取失敗を確認する。未確認を重複なしと扱わない。実行だけでは結果の完全性や内容を検証できない。既存の依頼へ足すなら、起票せずに 返信は `reply-issue.ts`、原因解消後の再試行は issue-desk-issue-control Skillの汎用 operation を使う。
- **重複候補の手がかり**: 相談開始前の題名の重なりでは止めず、HTTP 409・`duplicate_suspected` の候補も `duplicateHints` として受付AIへ渡す。`--not-duplicate "<理由>"`（1〜500文字）は互換の記録用で、候補の確認は省略しない。起票直前は目的と共通対象の根拠を照合する。
- **送る前に経緯を読む**: 以前の同じ目的の依頼が見つかったら、送る前に 汎用GETでその閉じた理由・失敗の理由・レビューの指摘を読み、依頼文に反映する。`create-issue.ts` が止めたときは一覧の依頼を読み、`--history-read "<読んだ要点>"` を付けて送る。`--draft` の回答の `#N` は下書きの project で確認される。
- 「TODOで」「TODOとして」「Draftで」「今は起票せずメモとして」と言われたら起票せず、下の「TODOとして保存する（起票しない）」で保存する。

## 起票の前に確かめる上限と止まり方

起票は、上限の中で実装が終わる見込みを立ててから送る。止まってから返信や再試行で直す前提で起票しない。

- **実装回数の上限**: 1件につき `assignments.json` の `implementationRunLimit`。実装AIを起動するたびに1回使う（issue-desk-worker の `internal/execution/execute.go`・`report_completion.go` の `r.Runs++`）。回答・修正指示で実装AIが再び動くときも、様式不備の補完でも使う。使い切ると `waiting` で止まり「実装回数の上限に達しました」と出る。返信では進まず、再試行には利用者のその依頼への承認の発言が要る（[issue-desk-issue-control](../issue-desk-issue-control/SKILL.md) の「再試行する」）。
- **そのほかの上限**: 重み付き使用量 `implementationUsageLimit`、レビューの保留 `reviewRoundLimit`、固定テストの修復 `fixedTestRepairRounds`。値は `assignments.json` を読み、ここへの記載を根拠にしない。
- **実装AIが読めるもの**: 対象リポジトリの作業ツリーだけ。他のリポジトリ（受付のコードを含む）、Gitea API、資格情報は読めない。受付AIが読めても実装AIは読めない。実装に要る他のリポジトリの契約（JSONの形、検査の内容、APIの応答）は、行番号で指すだけにせず依頼文へ写す。CLIの実出力のように実装AIが取れないものも、テストに要るなら写す。
- **1件に入れる量**: 単独でマージできる挙動の変更1つ。受入条件を並べ「これだけ先にマージしても意味があるか」で切り、切れるなら別の依頼にする（ファイル数が目安の4件に収まっていても分ける）。依頼文に見込み（変更するファイル数・行数）を書く。送信前の照合は「起票する」の手順に従う。実装AIの途中報告が見込みを超えたとき、または使用量の残り（単件GETの応答の `workerExecution` にある使用量と `implementationUsageLimit` の差）が直前の1回分より少ないときは、実装を続ける指示の返信を送らず、そのIssueを閉じてから分けて起票する。
- **変更範囲**: 受入条件に要るファイルが保存済みの変更範囲に入っているかを確かめる。範囲外だと実装AIが止まって質問し、回数を使う。
- **`create-issue.ts` の警告**: 「固定版を読めませんでした」「行範囲・節の指定が見つからない」などは送信を止めないが、読まずに送らない。出力から警告を除く絞り込みをしない。
- **送る順序**: 複数の依頼は1件ずつ送り、前の1件が起票できて実装の前提が崩れないことを確かめてから、次の依頼文に反映して送る。依存先がある依頼は、依存先のマージを確かめるまで送らない（他のリポジトリの共通番号は先行Issueに指定できない）。
- **返信の前**: 回数の使用数を確かめる。今の一覧・詳細の出力には回数の項目が無いので、コメントの「作業を開始しました」の数から見積もり、見積もりと明記する。質問や指摘は1回の返信にまとめて答える。
- **順に実装する**: 複数の依頼は、前の1件がマージされて結果を確かめるまで待ってから、次の1件を送る。前の1件で分かった前提の誤りは次の依頼文に反映する。
- **うまくいかないとき**: 利用者に聞く前に、AI自身が最後のコメント・記録・該当のコードを読んで原因を調べる。依頼文の前提が原因で実装回数を使い切ったときは、閉じて原因を直した依頼文で再起票してよい。再起票の前に、実装AIが読めない契約を本文へ写す。
- **相談や実装の側に原因があるとき**: 利用者が今のチャットで「割り込みで起票or直接PRで実装・マージまで進める」と明示した範囲では、受付AI・Worker・起票処理の不具合で再起票が通らないなら、割り込み（`--priority high`）で修正依頼を起票し、起票で直せないなら直接PRで実装してマージまで進める。明示が無いときは `chat-instructions.md` に従い、直し方と理由を示して利用者の明示を待つ（例外は chat-instructions.md の直接PRの項にある、「寝る」「任せる」「聞き返すな」の後に起票できない不具合の直し）。

## 依頼文の書き方

下の生成部分「依頼側と受付の共通の取り決め」を使う。Issue参照の照合手順は「送信前のIssue番号確認」を参照する。依存は先の成果物を使うときだけ書き、担当PCなど受付AIが読めない前提は本文に書く。

**変更するファイルを必ず書く**: 受付は優先度（割り込み・通常・自動）によらず、起票に変更・追加・削除するファイルの宣言（リポジトリのルート相対パス、ファイル単位）を求める。足りないと受付は起票せず質問を返し、往復になる。送る前に repo-search などで変更するファイルを特定し、本文に書く。受付が探して絞れる分は任せてよいが、依頼者が分かっているファイルは最初から書く。create-issue.ts は新規相談の本文にファイルが1件も無いと警告する。

**短く書く**: 依頼文は2000文字を目安にする。書くのは、目的・変更するファイルと挙動・受入条件・見込み・難易度の根拠・細部を任せる範囲と未決事項、以前の同じ目的の依頼が閉じた・失敗した理由の要点、受付AI・実装AIが自分で読めない事実（ログの要所の行、他のリポジトリの契約）、依存（先行の成果物を使うとき）、分ける・分けない理由（推定費用を含む）、必要なときの「## 利用者の判断と根拠」、assumptions（全依頼）と直し・調査・失敗の対応の prevention・similar（各1〜3行）だけにする。資料の引継ぎは `--read-evidence-file` で本文と別に渡す。対象リポジトリ内で実装AIも読めるコード・資料は説明や写しを書かずファイル:行で指し、対象リポジトリ内の規則の写し・調べた経過（similar の searched に書く検索の語・コマンドは除く）・既存依頼との照合の経過は書かない。ログ・出力は判断・テストに要る行だけを写す。省いた説明の補足は受付AIに聞かれたら返信で足す（変更するファイル・受入条件・見込みは最初から書く）。

## TODOとして保存する（起票しない）

利用者が「TODOで」「Draftで」「今は起票せずメモとして」と求めたときは、相談・Gitea起票を始めず受付のTODOへ保存する。本文中のIssueを上の「送信前のIssue番号確認」で照合し、[TODOの作成・本文更新・相談開始](refs/todo-edit.md) の汎用窓口を使う。

新規はPOST `/api/todos` と同じTODOの `/save` の2段階。初回にTODO IDと保存ID・両JSON本文を固定して記録し、作成だけの空TODOを保存成功としない。結果不明でも新しいIDや内容を作らず同じ要求を照合する。既存更新は現在revisionを読み、送信ID・画像保持・省略値と競合の手順を守る。本文は8000 UTF-16コード単位以内、画像は新規保存では付けない。

`provider` は相談後の実装先（既定codex）、`consultationProvider` は相談元。保存はどちらのAIも起動しない。通常の期限は1〜30日先、省略時の初回本文保存は保存時刻の7日後。期限・確認条件・一覧の全ページ・再送・相談開始の条件は参照手順にまとめる。

保存後に自動で相談・起票へ進めない。利用者が開始を依頼したときだけ、同じTODOの現revisionを読み `/start` を送る。`/start` の本文には相談の難易度 `tier`（light・standard・heavy）を必ず入れる（`--tier` と同じ基準で依頼元が選ぶ）。削除・取り下げなどは [issue-desk-admin](../issue-desk-admin/SKILL.md) の条件に従う。受付が使えない場合は別の経路へ回り込まず、未保存・未確認を区別して報告する。
