# 共通の接続と登録の詳細

[issue-desk-operations](../SKILL.md) の「共通の決まり」の続き。呼び出す前にこのファイルも読む。「下のトークン接続」はこのファイル、「TODOとして保存する（起票しない）」は同Skillを参照する。

- NASの窓口は `stage-watch.ts`・第1引数が `notice` の `desk-ops.ts`、および `reply-issue.ts` の `--over-limit-statement`・`--implementation-limit-retry`・`--approval-question`・`--approval-answer` 付き呼び出しを `~/.issue-desk/desk-pc`（稼働WorkerのK2のPCトークン接続）へ自動で振り分ける。それ以外の専用スクリプトは一時キー。汎用get/operationをPCトークンで使う場合はNASの `sh ~/.issue-desk/desk-pc` を明示し、[Issue操作・チャット承認](../../issue-desk-issue-control/refs/api-operations.md) に従う。振り分け一覧は `deploy/nas/desk-pc-routes.json` に一元管理する。
- NAS本体とUbuntuのPCでは窓口 `~/.issue-desk/desk <スクリプト名> …` で呼ぶ。NASは稼働Serverと同じ環境で一時キーを発行・消費する。Ubuntuは稼働WorkerのK2にある `serverUrl` とPCトークンで接続する。どちらも通常は接続引数を付けず、資格情報を表示しない。
- 汎用読取は `~/.issue-desk/desk desk-get.ts GET '/api/drafts?view=summary&limit=20'`。GET専用で既定1 MiB、`--max-bytes` は最大16 MiB。経路の `security` により一時キーやPCトークンでは読めない場合がある。NASでは一時キー、UbuntuではPCトークンを使い、自動切替しない。
- UbuntuのK2は `serverUrl`・`serverTokenFile`・`workerId` の3項目。窓口が設定を読めない場合は、同じPCの設定と配布結果を確認する。NASの窓口では `deploy/nas/intake.sh active` が書き手を一意に確認できることが前提。
- 窓口が無いときはそのPCの配布経路を確認する。NASは`deploy/nas/update-desk-access.sh`の一時キー接続、Ubuntuは`deploy/clients/remote-control/desk-access.sh`のPCトークン接続を使う。既存のトークンを発行し直さず、値を表示しない。ファイルと作業ディレクトリはホーム配下に置く。詳しい接続・診断・配布手順は[チャットとLinux PCへの配布](../../../docs/chat-operations.md)に従う。
- NAS本体以外の他のPCも、作業ツリーの `config.local.json` に `serverUrl` があれば引数なしで接続する。設定に `serverUrl` が無いPCからはトークン接続: 各スクリプトに `--url <受付のURL> --token-file <トークンのファイル>` を付ける（または環境変数 `ISSUE_DESK_URL`・`ISSUE_DESK_TOKEN_FILE`。受付のURLは `https://issue-desk.example.ts.net/`）。スクリプトはそのPCのissue-deskの作業ツリーのものを使う。トークンの値はコマンドライン・チャット・Issue・リポジトリに書かない。
- トークン接続で使えるのは、起票（相談の開始と回答）・読む・一覧/検索・クローズ依頼・TODOの作成と保存（自分のトークンで作ったTODOだけ）・PCの新しい引き取りを止める／戻す（[host-drain](../../host-drain/SKILL.md) の汎用窓口手順）だけ。許可の無いトークンでは、Issueへのコメント・停止・再開・再試行は403になる（再試行は利用者が受付画面の「再試行する」で送る）。範囲はIntakeの `api/openapi/00-header.yaml` と各経路の `security`・`x-issue-desk-delegate` で確認する。
- 利用者が受付画面でそのトークンに運用の代行を許したときだけ、トークン接続でもIssueへの再試行（[汎用窓口手順](../../issue-desk-issue-control/refs/api-operations.md)）・返信（`reply-issue.ts`）、要対応と回答待ちの相談の読み取り（`desk-alerts.ts`）、他の相談への回答（`create-issue.ts --draft`）、モデルの固定規則の確認・旧保存値の取消（[model-override](../../model-override/SKILL.md)）、Issueの優先度の変更（[priority-issue](../../priority-issue/SKILL.md)）、停止・再開・担当の引き継ぎ（[issue-desk-issue-control](../../issue-desk-issue-control/SKILL.md) の条件のときだけ）、既存のTODOの本文の書き換え（汎用窓口のGET/operation。[issue-desk-operations Skill](../SKILL.md) の「TODOとして保存する（起票しない）」）、要対応の確認済み・クローズ依頼の判断・相談の取り下げ・TODOの一覧と保存と削除（汎用 operation。`skills/issue-desk-admin/SKILL.md` の「要対応の確認済み・クローズ依頼の判断・相談の取り下げ・TODO」の条件のときだけ）が使える。削除の実行・相談の優先度・決定の記録は許しても403のまま（相談の優先度と決定の記録はNASの一時キーでは使える）。削除の承認と、相談の続行・代理の回答の取り消し・新しいプロジェクトの作成同意（同じ汎用窓口手順）は、利用者がチャットで対象を特定して承認した発言と、その発言の日時（`instructionAt`）を添えたときだけ使える。受付が別のPCにある設定（`config.local.json` の `serverUrl`）では、接続の引数なしで同じトークン接続になる。運用代行の条件は同じAPI仕様の `x-issue-desk-delegate` と各手順の入力検査に従う。
- 監視が開始するのは受付が起票したIssueだけ。Giteaへ直接立てたIssueは開始せず、作業の無いIssueへの `/codex run` でも開始しない（手動開始の目印も読まない）。登録の経路は、別のPCのチャットのAIは受付API（このSkillのスクリプト。他のPCからはトークン接続）と受付画面の相談で、実際の起票は受付だけが行う。監視がGiteaのコメントに投稿する後続の案から受付は起票しない（「自動監視からの新規起票は停止されています。」と記録するだけ）。受付AIが使えない間（受付の停止・クォータ切れ）は、使えるようになるまで登録を待ち、そのことを利用者に伝える。受付から登録した依頼の担当のPCを移して開始するのは、受付画面の「担当を引き継ぐ」か、[issue-desk-issue-control](../../issue-desk-issue-control/SKILL.md) の「Issueの停止・再開・担当を変える」の汎用窓口による担当変更（使ってよい条件のときだけ）。
