# 変更・運用操作の順序を点検する

複数の変更や運用操作を扱うとき、提案前と各段の実行前にこの手順を使う。操作の許可を得る手順や実行権限を追加するSkillではない。対象プロジェクトの指示と利用者が許可した範囲に従う。受付の接続・読取・操作は `skills/issue-desk-operations/SKILL.md`、利用者への報告は `skills/user-interaction/SKILL.md` に従う。

## 依存の向きと停止の影響

1. 操作ごとに対象リポジトリ、実行先、PC、必要な稼働版と完了条件を並べる。「Aの完了をBが待つ」と「Aを先に行うとBの実行・マージ・反映が停止または遅延する」を別々に書く。前提を作る変更と後続を止める変更を混同しない。
2. 反映を遅らせる変更は、それに依存しない修正を先にマージ・反映し、効果を確認した後に置く。反対の順序が必須なら、止まる処理と停止後にも進める経路の証跡を先に確認する。
3. 停止・一時停止・実行先や担当の切り替え・引き取り停止の前に、その対象に依存する公開待ち、実行待ち、再検証、再実装をすべて突き合わせる。自分の依頼だけでなく関連リポジトリと他PCの処理も含める。残る処理を先に流すか、停止後にもレビュー・再検証・公開・反映・資源の解放まで進められる経路を確認する。切り替え先の名前があるだけでは確認済みとしない。

既存の許可された読取経路を使う。Issueの状態・担当・待ち理由は issue-desk-issue-control Skillの汎用GET手順、要対応は `scripts/desk-alerts.ts`、PCの状態は GET /api/hosts を突き合わせる。一覧の絞り込み・上限・続きの有無を確認し、`hasMore` が false になるまで queryの `page` を増やして全ページを読み、関係する全件の詳細を集める。一覧の使い方は issue-desk-issue-control、接続と権限は issue-desk-operations の Skill を参照する。APIの応答・認証は `api/openapi/` で確認する。

## 資源の保持と待ちを点検する

各処理について、依存先、資源、保持者（PC・Issue・PR・セッション）、取得条件、解放条件、現在待つ相手、その相手が必要とする資源を表にする。依頼間の依存と、範囲保持・lease・マージの番を区別する。確認できない取得・解放条件は推測で補わず、未確認とする。

| 資源 | 確認する取得・解放と待ち |
| --- | --- |
| 依頼間の依存 | 先行依頼の成果物を使う場合だけ、受付が起票時に `job_deps` を記録する。先行依頼の成果物と `merged`・`closed` の状態を確認する。範囲の重なりや優先順だけで依存を付けない。 |
| 変更範囲の保持 | 同一リポジトリの全PCの `running` ジョブが範囲を保持する。`held`・`queued` は保持しない。配布可能な予約は同順位以下の重なる候補を待たせる条件として別に確認し、優先順と範囲保持を混同しない。 |
| lease | 受付がジョブを配布して `running` にすると取得し、所有PCが実装からマージまで延長する。所有PC・epoch・期限を照合し、lease を失ったらその場でやめる。`running` から外れると lease とそのジョブのマージの番を解放する。 |
| マージの番 | リポジトリごとにジョブまたは直接PRのマージ依頼の1件だけが保持する。所有PC・対象・epoch・期限を確認する。期限は15分で、期限切れは未保持として扱う。取得・延長・解放の条件とマージ直前の再確認は現行資料に従う。 |

仕事の配布・変更範囲・依存・マージの番は受付のIssue詳細（issue-desk-issue-control Skillの汎用GET）、優先度の割り込みの条件は [issue-desk-operations](../issue-desk-operations/SKILL.md)『起票する』を参照する。

「Aが資源を保持してBを待つ → BがAの資源を待つ」の循環や、進めない工程が資源を保持したまま後続を待つ順序を探す。停止を後ろへ置き、保持者を先に完了させて正規の解放を確認するか、既存の仕様で進められる経路を確認して順序を組み直す。記録の手編集や権限拡大で回避しない。循環を解消できない場合は、その結果に依存する操作を保留して理由を示す。

## マージと反映の時刻を分ける

PRがマージされた時刻と、必要なPC・稼働先でその版が動き効果が出る時刻を分けて見積もる。変更ごとに対象SHA、稼働版、反映経路、待ちの起点、条件と根拠資料を記録する。

- NASの監視は、ホスト側のsystemdタイマーが `deploy/nas/update.sh` を実行して更新する。コンテナは自分を更新しない。heartbeat の `busy` がある間はNAS watcherの入れ替えだけを見送る。受付が有効な構成では、受付の更新とclientイメージの発行は進める。起動確認と巻き戻しは `deploy/nas/update.sh` に従う。
- 各PCのclientイメージはNASから配布され、PCのホスト側の hostd が更新する。マージしたワーカーによる自己配置を前提にしない。チャット用Skill等のホスト配布はNASの更新処理とUbuntu PCの `issue-desk-rc-update.timer`（rc-update）を区別し、[チャットの運用](../../docs/chat-operations.md) に従う。
- CLI・Node・pnpm はイメージで固定し、起動後の待ちは置かない。版は `deploy/versions.json` で固定する。
- 起動時刻、設定値、公開待ちの状態や稼働版が未確認なら時刻を断定しない。「条件を満たした次の確認後」など条件付きの見込みと、未確認の根拠を日本時間で示す。

## 提案と段ごとの確認

利用者へ、順序・理由・何が何を待つか・各段の確認方法を示す。各段に「操作／待つ前提／確認対象と証跡／効く時刻の見込みと条件／次へ進む条件」を書く。公開待ち件数、対象PRのマージ記録とSHA、対象PCの稼働版、修正の効果、資源の解放など、次の段に必要な確認対象を先に決める。マージ記録だけで稼働先への反映済みとはしない。

確認できるまで、その結果に依存する次の段へ進まない。非同期の待ちの後は対象・版・状態を再照合し、途中で停止や切り替え、対象の変更があれば古い結果を使わず段取りを見直す。既定ブランチ更新時も関連資料・配布一覧・テストの差異を再確認する。

読取失敗、古い記録、省略された一覧、GET /api/hosts の理由付きの空一覧は「待ちなし」ではなく未確認として扱う。checkedAt・updatedAt・取得時刻・対象範囲を証跡に残す。直接読取できないAIは、提供資料と許可された確認経路の証跡に基づいて段取りを示し、未確認部分を明示する。操作権限・認証・実行範囲を広げず、資格情報の値を本文やログに書かない。API経路そのものが参照検査で検証済みとは扱わない。

## 利用者が説明した経緯からの例

以下は利用者が説明した経緯であり、番号の対応は未確認のため番号を付けない。

- Claudeに依存する公開待ち・再検証が残る状態で先に一時停止し、後続公開を止めた。誤った順序は「Claudeを一時停止 → 残る処理の公開・再検証」。避ける順序は「依存する全件を確認 → 公開・再検証を先に完了して結果を確認、または停止後も進める許可済みの経路を確認 → 一時停止」。実装の完了だけでClaudeが不要になったと判断しない。
- 公開待ち中の自己デプロイ見送りを先に導入し、後続修正の反映を遅らせた。誤った順序は「反映を見送る変更を導入 → それに依存しない後続修正をマージして反映待ち」。避ける順序は「独立した修正を先にマージ → 必要な稼働先への反映と効果を確認 → 見送りの変更を導入」。マージ順だけでなく、各変更が効く順番を確認する。
