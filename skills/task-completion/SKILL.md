# 依頼全体の完了まで続ける

実装の分割、PRのマージ、サブエージェントの完了は工程の完了であり、利用者の依頼全体の完了ではない。「着手して」も会話で合意済みの目的を引き継ぐ。作業量、応答の長さ、区切りのよさを理由に、目的を初回PR・基盤・試作へ狭めない。

## 作業台帳を保つ

依頼全体の目的、利用者が求めた成果物と完了条件、検証、許可済みの配置、片付けを作業ツリーの`.tmp/`（作業ツリーが無いときだけセッションのscratchpad）に記録する。最初の必須項目のIDを`originalRequirements`に固定し、現在の作業項目を`deliverables`へ持つ。利用者が求めた範囲を除く場合だけ、その対象IDと実際の利用者発言を`scopeChanges`へ記録する。AIの判断、エージェントの見積もり、技術的な都合は範囲変更の根拠にしない。

作業項目の状態は`pending`・`running`・`verified`・`blocked`。`verified`には成果物と実際の確認結果を示す証跡を付ける。実装済み、テスト済み、レビュー済み、マージ済み、配置済み、稼働確認済みを必要な粒度で別項目にする。未実装を拒否する安全措置だけでは、その機能を完了にしない。

## 分担した作業を回収する

サブエージェントには担当範囲、依存する契約、完了条件、必要な検証を渡す。`agents`には担当項目ID、状態、結果を回収したかを記録する。報告を受けたら変更と証跡を照合し、未完成の項目は親が継続するか再度委任する。全員が一区切りを報告したことを全体完了と読み替えない。

一部が待ちなら独立した許可済み作業を続ける。利用者が途中で質問や再発防止を追加したときは、先に質問へ答え、追加項目を台帳へ足して元の作業も続ける。サブエージェントの返答待ちや途中経過だけで最終返答にしない。

## 終了前の判定

最終返答を出す前に、実際の台帳を`node skills/task-completion/scripts/check-completion.ts --file <台帳の絶対パス>`で検査する。具体的な形式は同スクリプトの型定義を参照する。

- `complete`だけが依頼全体の完了。すべての必須項目に証跡があり、エージェントの結果を回収していることを実物でも照合する。
- `continue`なら作業を続ける。「残りがある」「次は行う」と書き添えて終了する代わりに、残件を実行・再委任する。
- `needs-user`は残件がすべて実証済みの利用者専用操作か外部の阻害要因で、独立して進められる項目もなく、エージェントの結果を回収済みの場合だけ。阻害要因・証跡・必要な操作を具体的にまとめ、全体完了とは報告しない。

改善・リファクタリング・見直しのように、依頼に完了の基準が無い依頼は、台帳に `kind: "open-ended"` を置く。見つけた指摘を直しただけでは完了にせず、差分を知らない独立した見直しを繰り返し、最後の見直しの結果を `finalReview` に記録する。`evidence` には見直しの記録、`findings` にはまだ直していない指摘、`kept` には残すと決めた指摘とその理由を書く。`findings` が空になるまで検査は `continue` を返すので、見直しと直しを続ける。難しさ・依存の強さ・量は、残す理由にしない。検査が確かめるのは、記録があること、未修正の指摘が無いこと、残す指摘に理由があることだけで、理由の中身や見直しを繰り返したかは確かめない。そこは自分で守る。

利用者の明示的な停止・取消・範囲変更を優先し、既存の権限や利用者専用の承認を越えて完了させようとしない。検査は台帳の整合を確認するもので、証跡の真実性や既存の許可条件を代替しない。終了を自動で遮断する機構がない実行環境でも、この判定を省略しない。
