# Intake Client

ブラウザで動く画面を独立してビルドし、Go Serverへ静的ファイルを渡す。
Node.js 24以上を使い、`pnpm install --frozen-lockfile`、`pnpm typecheck`、
`pnpm test`、`pnpm build`で検証・ビルドする。
ビルドと型検査には、同じリポジトリの`client/`、`api/`、`shared/src/`が必要。

## 配置の契約

- 配置する成果物は`dist/`のみ。ServerやWorkerのソースを参照しない。
- Serverは`dist/index.html`を`/`で配信し、HTMLは`Cache-Control: no-store`にする。
- `dist/ui-version.json`の`ui`を`GET /api/health`の`ui`として返す。
- `/v/<ui>/`以下の静的ファイルには、その版と内容が一致する場合だけ
  `Cache-Control: public, max-age=31536000, immutable`を設定できる。
- `dist/index.html`は、`app.js`が静的にimportするモジュール（その先のimportを含む）を
  `<link rel="modulepreload">`で`/v/<ui>/`の版付きパスに並べ、importの段ごとの取得待ちをなくす。
- `/sw.js`は版なしで配信し、更新確認できるよう`no-store`にする。
- APIと静的画面は同一Originで配信する。画面の認証はCookie、変更操作はCSRFを使う。
- リアルタイム更新には`GET /api/events`のSSEを使い、切断時も既存の定期取得を継続する。

## 一覧の更新間隔

一覧の差分取得は、SSE接続を確認できる間だけ30秒間隔にする。
接続を持つタブはSSEの接続完了で確認し、他の表示中のタブは共有された通知または接続状態で確認する。
接続状態は5秒ごとに共有し、15秒届かなければ確認を失効させる。
接続を確認できない表示中のタブ（未接続・接続待ち・切断後）は15秒間隔で取得する。非表示のタブは定期取得をせず、表示に戻ったときに読み直す。
切断からの復帰時の全体照合、通知による行の個別取得、保留50件超の全体照合、取得開始の最短3秒間隔は維持する。

各PCの負荷・要対応の自動処理など、通知されない欄は定期取得で反映する。
接続確認中は変更から次の取得まで最大30秒、それに取得・描画時間が加わる。
周期は取得完了後から数えるため、取得中に読取済みの欄が変わると、実行中の取得の残り時間も加わる。
通信失敗・読取元の欠測・ブラウザーの非表示時のタイマー制限がある場合は、反映時間の上限を保証しない。

## 一覧の取得範囲

要対応・実行中・待機中・停止中のタブは有効範囲（`GET /api/list?tabs=active`）、
フォローアップ・TODO・完了・クローズ済みのタブは全範囲（`tabs`なし）を取得する。
全範囲を要するタブを離れても60秒は全範囲の保持と差分取得を続け、その後の最初の取得で有効範囲の全体応答に置き換える。
有効範囲を保持している間、全範囲を要するタブの件数は「—」と表示し、そのタブを開いたときに全範囲を読む。
再読み込みで復元した全範囲の保持も、開いたタブが有効範囲で足りるなら最初の取得で有効範囲に置き換える。

## Issue詳細の更新間隔

Issue詳細の定期取得（`view=summary`）も、SSE接続を確認できる間だけ30秒間隔にする。
接続の確認と失効は一覧と同じで、確認できない間は10秒間隔で取得し、予約済みの取得も切り替え時に周期を計算し直す。
受付の通知（そのIssueの`issue`）は接続中も次の取得を前倒しする。
受付を通らない変化（Giteaでの直接の操作、WorkerがGiteaへ直接書くコメント）は通知されず、接続確認中は反映まで最大30秒、それに取得・描画時間が加わる。

## 相談の更新間隔

相談の定期取得（`GET /api/drafts/{id}`）は、SSE接続を確認でき、受付の処理が動いていない間だけ30秒間隔にする。
動いているとみなすのは、受付AIのターンの実行中・順番待ち・自動の再試行の予約中、前回の処理の終了中、起票の処理中、分割した子の残りがある間。
この間と、接続を確認できない間は5秒間隔で取得し、予約済みの取得も接続の切り替え時に周期を計算し直す。
動いているかは最後に読めた応答で判定し、受付の通知（その相談の`draft`）は接続中も次の取得を前倒しする。
相談の保存を伴わない変化は通知されず、動いていない間は反映まで最大30秒、それに取得・描画時間が加わる。

## ソースの構成

`src/api/client.ts`が通信境界で、`src/ui/`が画面と状態型を持つ。
すべてTypeScriptで実装し、`tsconfig.json`のstrict設定を使う。
`pnpm typecheck`は共有スコープの画面断片を1つの仮想モジュールとして検査し、
Service WorkerはWebWorkerの型で別に検査する。

画面は複数の断片で同一スコープを共有する。
`scripts/app-parts.json`の依存順でビルド時に結合し、最後に一度だけ`boot()`を呼ぶ。
純粋な表示用分類処理の正本は`shared/src/desk-attention.mts`に置き、
`src/ui/request-classification.ts`から再exportする。画面の配布物には同じ本文をコンパイルして含める。
業務上の操作許可はAPIの応答に従い、Clientを認可の根拠にしない。

## 検証

通信のCSRF・認証・拒否応答・再送抑止・中断、静的ビルドの依存閉包と版固定を検証する。
画面更新は入力中の更新保留、復元、再読込ループ防止を検証する。
`ISSUE_DESK_TEST_CHROMIUM`にChromiumの実行ファイルを指定すると、
実ブラウザでIssue・相談・TODO・管理画面・新規プロジェクト・稼働実績の遷移、
CSRF付き返信、新規依頼からのTODO保存、SVGグラフを検証する。
リポジトリ表示の回帰検証（`node --test test/repository-display.test.ts`）は常に実ブラウザで実行する。
`ISSUE_DESK_TEST_CHROMIUM`が未指定のLinux x64では開発依存の固定版Chromium Headless Shellを使い、
ほかの環境ではPATHの`chromium`を使う。任意のChromiumを使う場合は同変数で実行ファイルを指定する。
表示文字と利用者向け属性を検査し、通信・リンク・入力値・データ属性、会話の原文、同名衝突の完全名を区別する。
テストAPIは一時的なlocalhostのHTTPサーバーで動作する。
Linux x64で指定したChromiumのプロファイル排他処理がUnixソケットの権限拒否で起動できない場合は、
開発依存に版を固定したChromium Headless Shellで同じ操作と検証を実行する。
展開先は試験ごとの一時ディレクトリとし、DevToolsの接続先はブラウザの起動出力から取得する。
それ以外の起動失敗や画面検証の失敗はそのまま不合格にする。

読み取り専用の画面テストは同一テストプロセス内で配布物を共有する。
