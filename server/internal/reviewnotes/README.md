# 注意点の日次処理

`Service.Run(ctx, repo, config)` がリポジトリ単位で処理する。設定は配備する
`assignments.json` の `reviewNotes` オブジェクトを `ParseConfig` へ渡す。
省略時の既定値は回数2・60日・4000バイト。起動時と既存の起票結果照合の1分周期から
全対象リポジトリへ呼び出す。新しいタイマーは作らない。共通のキャンセルと終了待ちを
使うため、Serverの停止時は実行中のAIを中止し、使用量の記録と処理の終了を待つ。
周期の中では起票結果の照合後に日次処理を非同期で開始する。日次処理は同時に1本だけ
動かし、AI枠待ち・AI実行中も起票結果照合の1分周期を継続する。
呼び出し元が `Service.Classify` に `AIClassifier` を設定する。
`finding` / `followup` は受信記録の種類で、採用規則の意味的な `kind` とは別物。
有効な新しい行があるのに種類分けが未接続なら、試行日だけ残してエラーにする。

## AI分類と既知の再利用

- `notes.classifications` にリポジトリ・分類版・期限・元の行と分類結果を保存する。
  省略された旧状態では空として扱う。リポジトリ・受信種類・本文（切り詰め前）の
  完全一致、現在の分類版、期限内を要求し、さらに元の `repo_notes` 行のID・Issue・
  受信時刻・種類・本文をDBで照合する。不明・不一致・曖昧な保存値は再利用しない。
  期限は元の行の受信時刻からstaleDays後。再利用で期限を延ばさない。
  保存する分類は最大200件、元本文は各4000バイト以下に制限する。長い本文は
  分類結果を採用できるがキャッシュせず、上限超過時は古い保存順から除く。
  旧状態も次の正常な更新時に同じ上限へ整理する。除外された行は再出現時に再分類する。
- 既知の行はAIへ送らず、未知の行だけ送る。全件既知または新しい行がなければ
  AI枠の取得・モデル解決・AI呼び出し・使用量行の作成を行わない。
- 指摘の本文は400文字以内（UTF-16単位でも400以内）に切り詰めてJSONへ符号化する。
  既存の種類も各400文字・最大200件を参考データとして渡す。固定プロンプトが本文・
  種類を信頼しないデータとして区切り、命令を実行・解釈しないよう指示する。
  CLIは既存の道具なしの経路を使い、シェル・検索・外部操作の道具を渡さない。
  CLI自身の契約サービスへの通信は既存のまま必要になる。
- 既存のAI枠と配置待ちを通った後に、注意点の更新の固定モデル（工程 `reviewNotes`。
  Claude は haiku、Codex は codexEquivalents の haiku 相当、推論レベル low）と現在の一時切り替えを
  解決する。使用量は成功・失敗・停止とも既存の記録口へ工程「注意点の更新」（`usage.ReviewNotesStep`）で保存する。
  別の実行先への独自のフォールバックや、同日のAI再試行はしない。
- 配備される `server/schemas/review-notes.schema.json` で応答を検証する。根拠quoteが
  実際に送った本文に含まれない割り当て、未知の行ID、同じ行への複数割り当ては集計・
  再利用の保存から除く。形式不正・AI失敗・タイムアウト・使用量保存失敗では試行日だけ
  残し、採用結果・分類・cursorは同じJSONのまま保つ。翌日に同じ行を再処理する。
- プロンプト・分類規則・根拠検証を変更するときは `classificationVersion` を上げる。
  既存の種類は意味が同じ場合に再利用し、新しい種類名は英小文字・数字・ハイフンとする。

## 読取・採用・保存

- DB接続の待ちが終わってから日本時間の日付を決め、既存の移行10の
  `repo_note_processing.attempt_date` を原子的に確定する。同日と未来日の試行は
  再実行しない。この確定が失敗した場合は読取・種類分けをしない。
  プロセス内ではリポジトリごとの確認済み日を記憶し、同日以前の周期でDB確認を省く。
  試行日の保存に失敗した場合と確認中に日付をまたいだ場合は次の周期に再確認する。
  再起動後はDBの試行日を再確認する。
- `repo_notes` の `cursor` より後の `finding` / `followup` をid昇順で最大200行読む。
  `data.issue` は正の整数、`data.text` は空白だけでない文字列を要求する。
  受信APIはdataをオブジェクトとして保存するだけなので、ここで検証する。
  期限は本文内の `at` ではなく、受信側が保存した列 `at` で判定する。
  古い・不正な行も消費したcursorへ含め、後続の行を塞がない。
- 分類の出典は `NoteID` で照合する。存在しない行への分類や、同じ行への複数の
  割当は数えない。種類ごとのIssue集合を保存し、同一Issueの再報告は1件と数える。
  最低2件かつ設定された回数以上で採用する。
- 採用済み・候補とも最後の出現から `staleDays` を超えたら外す。ちょうど期限の
  行は残す。textのUTF-8バイト数合計が上限を超えると、出現Issue数が少ない順、
  同数なら最後の出現が古い順に候補へ戻す。完全な同順位はkind順で決める。
- `notes` は `items` / `candidates` / `removed` / `cursor` / `updatedAt` を持つ。
  各項目は `kind` / `text` / `issues` / `lastSeen` を持ち、時刻はUTCのRFC3339形式。
  `removed` は今回期限切れになった項目。候補へ戻した項目の出典は保持する。
  SQL NULL・JSON null・旧状態の省略された項目は空として読む。
- 種類分け・読取・保存の失敗時は試行日だけ残し、notesとcursorを変更しない。
  日付が別の試行に変わっていたら古い実行結果を保存しない。
  `improvement_cursor` は読み書きしない。
- fleetの既存配信は採用された `{kind,text}` だけ返し、集計情報を渡さない。
  保存されたnotesの型が不正な場合は、そのリポジトリだけ空配列として配信する。
  ほかのリポジトリと構成の配信は続け、保存値は書き換えない。

## 検証と復旧

通常のGoテストに採用・期限・同数・UTF-8上限と省略状態のテストを含める。
日次抑止は専用PostgreSQLの隔離スキーマへ配備する移行10のDDLをそのまま適用し、
`Service.Run` の実際の試行日保存SQLで
初回の読取失敗後の同日再実行、別のService・リポジトリ、日本時間の日付またぎ、
過去日の呼出し、試行日保存失敗を検証する。このテストはPostgreSQL固有の
並行実行・JSON保存や、受信から配信までの結合検証の代わりにはならない。
`ISSUE_DESK_TEST_POSTGRES_DSN` が指定されたときは、`issue_desk_test` で始まる
専用DB内の隔離スキーマへ実際の移行を適用し、受信の `jobs.Note` から保存・
配備設定を使う `fleet.ClientConfig` まで、並行試行・各段階の失敗も検証する。
未設定時のDBテストはskipであり、DB検証成功を意味しない。

処理の失敗なら試行日を消さず、原因を解消して翌日同じcursorから処理する。
採用規則の不具合から復旧する場合は呼び出し元を停止し、既存のDBバックアップから
対象リポジトリの `notes` 列だけを復元する（cursorもnotes内）。試行日と
`improvement_cursor` を変えず、配信結果と翌日の再処理を確認する。
旧状態のitemsに `lastSeen` がない場合、配信では読めるが、次の更新で期限切れとして
removedへ移す。復元したnotesの型が不正なら空配列が配信されるため、復元後には
対象リポジトリの配信内容も確認する。
分類キャッシュもnotesと一緒に復元する。旧状態のバックアップに分類がなければ
未知として分類し直すため、キャッシュだけを別に復元しない。

AI分類の固定テストは本文の上限・命令文のJSON化・両CLIの道具なし引数と出荷スキーマ、
実際の移行・`jobs.Note`・担当表・fleetを使う既知の再利用、未知だけの選択、失敗後の
同日抑止と翌日の再開を含む。startupのテストは既存周期の即時実行・停止待ち、枠待ち後の
一時切り替えと使用量保存、AI枠待ち・実行中にも次の照合周期が動くことを検証する。
通常の `go test` で専用DSNを省略した場合、DBテストは未検証である。
固定検証の `scripts/verify.sh` と注意点だけの `scripts/verify-review-notes.ts` は、
DSN未指定なら共通の `scripts/with-test-postgres.ts` で隔離PostgreSQLと専用DBを準備する。
本番と同じPostgreSQL 17.11の配布物を版・SHA-512固定で取得し、実際のエンジンを使う。
ループバックの空きポートだけを使い、全検証に同じ専用DSNを渡す。終了・失敗・中断時に
停止と一時領域の削除を行う。明示したDSNは検証専用名を要求し、接続先を書き換えない。
実行条件と取得済みバイナリの指定方法はルートREADMEの「開発と検証」を参照する。
必要なテスト全件のPASSは引き続き必須。GoのJSONイベントを照合するため、
未実行・SKIP・名前の消失・子テストの
SKIPも成功にならない。`-count=1` で再実行し、各テスト名とPASSを検証ログに出す。
接続文字列は出力しない。失敗時は接続情報を伏せたGoの診断を出力する。
注意点に絞った確認は、リポジトリの根から `node scripts/verify-review-notes.ts` を実行する。
